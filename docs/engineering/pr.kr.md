## 하는 일

`pr`은 풀 리퀘스트 본문의 형태를 정의합니다. 변경을 보여 주는 **Summary**, 동작한다는 **Evidence**, 그리고 반영하는 것이 얼마나 위험한지에 대한 **Merge Danger** 판단입니다. 이것은 워크플로가 아니라 형식 참조입니다. 브랜치를 푸시하거나, PR을 열거나, 무엇이 들어갈지 결정하지 않습니다. [에이전트](https://www.aihero.dev/ai-coding-dictionary/agent)가 본문을 작성할 때 그것이 어떤 모습이어야 하는지 알려 줍니다.

요약은 단락이 아니라 시각 자료입니다. 기본적인 PR 본문은 diff를 산문으로 설명합니다. 이 스킬은 핵심 요점을 명확하게 만드는 **가장 작은 뷰**(의사 코드, 호출 트리, 컴포넌트 트리, 파일 트리, Mermaid 다이어그램, 또는 형태를 잡은 diff)를 고르고, 그 주변의 말은 짧게 유지합니다. 리뷰어는 이미 diff를 열어 두었으므로, 본문은 리뷰어가 diff를 읽기 전에 그 형태를 보여 줍니다.

## 언제 사용하는가

`/pr`을 입력하거나, 에이전트가 PR 본문을 작성할 때마다 자동으로 사용합니다.

| 상황 | 사용할 것 |
| --- | --- |
| 브랜치가 준비되었고 리뷰어가 훑어볼 수 있는 본문이 필요함 | `pr` |
| 코드는 작성되었지만 아직 아무도 리뷰하지 않음 | 먼저 [code-review](https://aihero.dev/skills-code-review), 그다음 `pr` |
| PR이 열려 있고 리뷰 댓글이 돌아오고 있음 | 이 세트에는 아직 없음. `pr`은 본문만 작성함 |

## 템플릿

세 개의 섹션이 이 순서로 있습니다.

- **Summary**: 하나 이상의 작은 시각 자료로, 각각 그것이 뒷받침하는 짧은 텍스트 옆에 배치됩니다. 하나를, 때로는 여러 개를 사용하며, 모두를 사용하는 일은 드뭅니다. 리뷰어가 필요로 하는 호출, 파일, prop, 경계만 남기십시오.
- **Evidence**: 전과 후입니다. 변경이 시각적이고 [환경](https://www.aihero.dev/ai-coding-dictionary/environment)이 스크린샷을 찍을 수 있다면, 스크린샷이 가장 강력한 증거입니다. 그렇지 않다면, 실패했다가 이제 통과하는 정확한 테스트를 의사 코드로 작성하거나, 바뀐 콘솔 출력을 사용하십시오.
- **Merge Danger**: 변경이 **일방향 문(one-way door)**인지 **양방향 문(two-way door)**인지, 그리고 그 **영향 범위(blast radius)**입니다. 양방향 문은 되돌리는 비용이 적습니다. 일방향 문(파괴적인 마이그레이션, 공개 API 제거, 되돌리기 어려운 결정)은 그렇지 않습니다. 영향 범위는 변경이 잘못되었을 때 무엇이 깨질 수 있는지를 명시합니다. 레이아웃 이동, API 사용자, 모바일 반응성 등입니다.

문 판단이 핵심 개념입니다. 이는 "병합해도 안전한가?"를 직감에서 리뷰어가 반박할 수 있는 명시된 주장으로 바꿉니다. 또한 리뷰어에게 [사람의 리뷰](https://www.aihero.dev/ai-coding-dictionary/human-review)를 어디에 써야 할지 알려 줍니다. 영향 범위가 작은 양방향 문은 훑어보고, 일방향 문은 천천히 읽으십시오.

## 자주 묻는 질문

**에이전트 자신의 문 판단을 신뢰할 수 있습니까?**

맹목적으로는 아니며, 그것이 판단을 명시하는 이유입니다. 변경을 작성한 에이전트가 그것을 평가하는 것이므로, "양방향, 작은 영향 범위"라고 말할 때 가장 의심하십시오. diff는 변경을 되돌릴 수 있는지도 종종 숨깁니다. 한 사용자의 말처럼 "커밋을 롤백한다고 보낸 이메일 묶음이 취소되지는 않으며", 플래그로 제어되는 롤아웃은 첫 번째 쓰기가 새로운 형식으로 기록되기 전까지만 양방향으로 남습니다. 스킬은 에이전트에게 체크리스트가 아니라 정의(파괴적인 작업과 되돌리기 어려운 결정은 일방향이다)를 제공하므로, Merge Danger 줄을 가장 주의 깊게 확인하십시오. 두 가지가 도움이 됩니다. 에이전트가 diff만이 아니라 [티켓](https://www.aihero.dev/ai-coding-dictionary/ticket)이나 [명세](https://www.aihero.dev/ai-coding-dictionary/spec)를 앞에 두도록 하고, 저장소가 항상 일방향으로 취급하는 변경(스키마 마이그레이션, 외부로 내보내거나 삭제하는 모든 것)을 에이전트가 판단하기 전에 읽을 곳에 적어 두십시오.

**PR을 대신 열어 줍니까?**

아니요. `pr`은 본문만 다룹니다. [implement](https://aihero.dev/skills-implement)는 현재 브랜치에 커밋하는 것으로 끝납니다. PR을 여는 스킬이나 옵션(`/to-pr`, 또는 커밋 대신 PR을 여는 `implement`)에 대한 요청은 아직 열려 있는 제안입니다. 한 사용자의 우회책은 PR을 열라고 지시하는 한 문장짜리 `implement`의 로컬 재정의입니다. [implement-spec](https://aihero.dev/skills-implement-spec)은 예외입니다. 이슈 트래커가 PR을 통해 작업을 종료하거나 사용자가 요청하면 초안 PR을 엽니다. `pr`은 모델 호출 스킬이므로, PR을 열라고 요청할 때마다 에이전트는 본문에 이 형태를 사용합니다.

**그저 또 다른 텍스트와 다이어그램의 벽을 만들어 내지 않습니까?**

스킬은 그것을 막도록 설계되었지만, 여전히 일어날 수 있습니다. 에이전트의 PR 본문에 대한 사용자들의 불만은 일관됩니다. "요약은 긴데, 내가 알아야 할 것은 무엇이 바뀌었는지, 어떻게 검증되었는지, 무엇이 깨질 수 있는지, 병합해도 안전한지뿐이다." 스킬은 에이전트에게 서두를 건너뛰고, 산문을 짧게 유지하고, 가장 작은 뷰를 고르라고 지시합니다. 대개 하나의 시각 자료이며, 모두를 사용하는 일은 드뭅니다. 그래도 다이어그램 더미를 받는다면, 에이전트가 그 지시를 무시한 것입니다. diff가 거대해서 본문이 거대하다면, 문제는 PR의 크기이며, `pr`이 그것을 나누어 주지는 않습니다.

**저장소에 이미 PR 템플릿이 있습니다. 어느 쪽이 우선합니까?**

기본적으로는 어느 쪽도 아닙니다. `pr`은 자체 템플릿을 가지며, `.github/pull_request_template.md`나 그와 비슷한 것을 찾지 않습니다. 여러 사용자가 스킬이 저장소의 템플릿을 사용하도록 요청했습니다. 아무것도 하지 않으면, 에이전트는 같은 문서에 대해 두 개의 경쟁하는 지시를 갖게 됩니다. 저장소의 에이전트 문서에서 이를 정하십시오. 예를 들어, 저장소 템플릿을 채우고 그 아래에 Summary, Evidence, Merge Danger를 두는 식입니다.

**출력이 HTML입니까? Mermaid 다이어그램은 왜 렌더링되지 않습니까?**

출력은 HTML 페이지가 아니라 마크다운 PR 본문입니다. GitHub와 GitLab은 PR 설명의 Mermaid 블록을 렌더링하지만, 터미널은 그렇지 않으므로, 에이전트가 아직 로컬에서 보여 주는 동안에는 다이어그램이 원시 텍스트처럼 보입니다. CLI 하네스의 사용자들은 ASCII Mermaid 렌더러를 사용하거나 에이전트에게 PR에 HTML 버전을 첨부하게 하는 방식으로 우회했습니다. Mermaid는 여섯 가지 뷰 중 하나입니다. 호출 트리, 파일 트리, 형태를 잡은 diff는 어디서나 똑같이 읽힙니다.

**돌아오는 리뷰 댓글을 분류해 줄 수 있습니까?**

아니요. 본문을 작성하고 멈춥니다. 사용자들은 다른 개발자나 리뷰 봇의 댓글을 분류하는 방법(어떤 것이 조치할 가치가 있고, 어떤 것이 문제가 아닌지)을 여러 번 요청했습니다. 이 스킬은 그것을 하지 않습니다.

**PR이 바뀌면서 본문을 최신 상태로 유지합니까?**

아니요. 한 시점에 본문을 작성하며, 리뷰 중에 바뀌는 PR은 그 본문을 낡게 만듭니다. 큰 변경 후에는 에이전트에게 본문을 다시 작성하라고 요청하십시오. 에이전트가 다시 PR 본문을 작성하는 것이므로, 같은 형태를 사용합니다.

**제 변경에는 UI가 없습니다. Evidence에는 무엇을 넣습니까?**

스크린샷을 제외한 모든 것입니다. 스크린샷은 변경이 시각적일 때만 가장 강력한 증거입니다. 마이그레이션, 백그라운드 작업, 리팩터링의 경우, 증거는 이전에 실패했고 지금 통과하는 정확한 테스트, 또는 바뀐 콘솔 출력입니다. "테스트가 green이다"만으로는 전후 비교가 아니라 주장일 뿐입니다.

**본문이 LLM에 의해 작성되었다고 표시할 수 있습니까?**

스스로는 아닙니다. 한 사용자의 방법은 저장소의 에이전트 문서에 에이전트가 작성하는 모든 이슈, 댓글, PR이 공개 문구 한 줄로 끝나도록 하는 상시 지시를 두는 것입니다. 그 규칙은 한 종류의 문서를 위한 템플릿이 아니라, 에이전트가 게시하는 모든 것을 다루는 저장소에 속합니다.

## 제대로 동작하고 있다면

- diff를 열기 전에 Summary 시각 자료만으로 PR이 무엇을 바꾸는지 알 수 있습니다.
- 본문에 서두가 없습니다. Summary 제목에서 시작합니다.
- Evidence 섹션이 테스트가 통과한다는 주장이 아니라 전과 후를 보여 줍니다.
- 모든 PR이 문과 영향 범위를 명시하며, 일방향 문이 속도를 늦추는 곳입니다.

## 어디에 위치하는가

빌드가 풀 리퀘스트로 출시될 때 `pr`은 리뷰와 회고 사이에 옵니다: `to-spec → to-tickets → implement → code-review → pr → retro`. 모델 호출 스킬이므로, 에이전트가 그 연쇄 밖에서 PR 본문을 작성할 때마다 스스로 실행되기도 합니다.

- [code-review](https://aihero.dev/skills-code-review)가 그 앞에서 실행됩니다. PR 본문은 이미 리뷰된 diff를 기술해야 하기 때문입니다.
- [implement](https://aihero.dev/skills-implement)가 본문이 기술하는 커밋을 만들어 냅니다.

상황에 어떤 스킬이 필요한지 확실하지 않을 때는 [ask-matt](https://aihero.dev/skills-ask-matt)가 세트 전체에 걸쳐 안내합니다.
