## 하는 일

`tdd`는 테스트 우선으로 기능을 구현하거나 버그를 수정합니다. 실패하는 테스트 하나, 그것을 통과시킬 만큼의 코드, 그다음 동작입니다. 그 루프가 보존할 가치가 있는 테스트를 만들어 내도록 하는 표준을 담고 있습니다. 좋은 테스트란 무엇인지, 테스트를 어디에 두는지, 목은 무엇을 위한 것인지, 그리고 테스트 스위트를 쓸모없게 만드는 세 가지 안티 패턴입니다.

먼저 합의하지 않은 시임에서는 어떤 테스트도 작성하지 않습니다. 테스트가 존재하기 전에, 테스트하려는 공개 경계를 명시하고 사용자의 확인을 위해 멈춥니다. 테스트 노력은 유한하며, 이 단계는 그 노력을 모든 엣지 케이스가 아니라 중요한 경로에 씁니다. `tdd`는 또한 진행자가 아니라 **참조**입니다. 루프의 규칙을 담고 있으며, 그것을 적용하는 [세션](https://www.aihero.dev/ai-coding-dictionary/session)은 다른 무언가(사용자, 또는 [implement](https://aihero.dev/skills-implement))가 실행합니다.

## 언제 사용하는가

`/tdd`를 입력하거나, 작업이 적합할 때 [에이전트](https://www.aihero.dev/ai-coding-dictionary/agent)가 자동으로 사용합니다. 테스트 우선으로 기능을 구현하거나 버그를 수정할 때, 또는 "red-green-refactor"라고 말할 때입니다.

입력과 관찰 가능한 출력을 가진 구체적인 동작을 구현해야 하고, 리팩터링에도 살아남는 테스트를 원할 때 사용하십시오.

| 상황 | 갈 곳 |
| --- | --- |
| 정의된 입력과 출력을 가진 동작(비즈니스 로직, 요청/응답 계약, 변환, 검증) | `tdd` |
| 동작이 아직 확정되지 않음 | 코드가 작성되기 전에 테스트 시임도 합의하는 [to-spec](https://aihero.dev/skills-to-spec) |
| 질문이 실제로는 테스트가 아니라 인터페이스의 형태임 | [codebase-design](https://aihero.dev/skills-codebase-design) |
| [명세](https://www.aihero.dev/ai-coding-dictionary/spec)나 [티켓](https://www.aihero.dev/ai-coding-dictionary/ticket)이 있으며 구현 전체를 대신 실행하기를 원함 | 티켓마다 `tdd`를 진행하는 [implement](https://aihero.dev/skills-implement) |
| 구성, 연결, 접착 코드, 타입 주석, 단순한 CRUD 위임 | 여기에 잘 맞는 것이 없음. 아래의 열린 빈틈 참조 |

마지막 행은 실제 빈틈입니다. 스킬은 시임을 *어디에* 둘지 결정하지만, 변경이 루프를 돌릴 가치가 *있는지*를 결정하는 것은 그 안에 없습니다. 대조하여 단언할 독립적인 진실 공급원이 없는 변경에 이를 실행하면, 구현을 다시 진술하는 테스트를 얻게 됩니다. 그것이 스킬이 경고하는 동어 반복적 안티 패턴이며, 반대 방향에서 도달한 것입니다. 이것은 [issue #746](https://github.com/mattpocock/skills/issues/746)이며, 열려 있습니다. 그것이 종료될 때까지, 그 판단은 직접 하거나 `CLAUDE.md`에 규칙으로 작성하십시오.

## 사전 요구 사항

[codebase-design](https://aihero.dev/skills-codebase-design)이 설치되어 있어야 합니다. `tdd`는 예전에 자체적인 깊은 모듈과 인터페이스 설계 노트를 담고 있었지만, v1.0에서 공유 스킬을 위해 그것들을 삭제했으며, 이제 `tdd`는 그 인터페이스 설계 어휘를 사용합니다. 그 밖에는 아무것도 필요 없습니다. 스킬은 [상태를 유지하지 않으며(stateless)](https://www.aihero.dev/ai-coding-dictionary/stateless) 자체 파일을 작성하지 않습니다.

## 루프, 그리고 그것이 실행되는 시임

이 스킬은 세 가지 용어에 기반합니다.

**Red-green.** 실패하는 테스트를 작성한 다음, 그것을 통과시킬 만큼의 코드만 작성하십시오. 그다음다음 테스트를 위한 코드를 작성하지 마십시오. 리팩터링 단계는 없습니다. 에이전트가 거의 수행하지 않았으며, 리뷰와 구현이 별도의 세션으로 더 잘 동작하기 때문에 스킬은 2026년 6월에 이를 제거했습니다. 리팩터링은 [code-review](https://aihero.dev/skills-code-review)에 속합니다.

**수직 슬라이스.** 하나의 시임에서 하나의 테스트를 작성한 다음, 최소 구현, 그다음 반복합니다. 첫 번째 사이클은 단일 경로를 종단 간으로 증명하는 **트레이서 불릿(tracer bullet)**입니다. 그 반대는 수평 슬라이싱입니다. 모든 테스트를 먼저, 그다음 모든 코드입니다. 일괄로 작성된 테스트는 *상상한* 동작을 검증합니다. 사용자가 하는 일이 아니라 사물의 형태를 확인하며, 구현을 이해하기 전에 테스트 구조를 확정하게 만듭니다.

**사전 합의된 시임.** 시임은 내부로 손을 뻗지 않고 동작을 관찰하는 공개 경계입니다. 이 규칙에는 예외가 없습니다. 확인되지 않은 시임에는 어떤 테스트도 두지 않습니다. 전체 연쇄에서는 시임이 더 일찍, [to-spec](https://aihero.dev/skills-to-spec) 중에 합의됩니다. "`/tdd`는 사전에 합의된 테스트 시임에서만 작업하라는 지시를 받고, `/code-review`는 합의된 테스트 시임만 사용되었는지 확인한다." 단독으로 호출되면, `tdd`는 사용자에게 직접 묻습니다.

막기 위해 작성된 세 가지 안티 패턴:

| 안티 패턴 | 징후 |
| --- | --- |
| 구현에 결합됨 | 동작은 바뀌지 않았는데 내부 함수의 이름을 바꾸면 테스트가 깨집니다. 목으로 대체된 내부 협력자, 단언된 호출 횟수, 인터페이스 대신 검증에 사용된 데이터베이스 쿼리. |
| 동어 반복적 | 기대값이 코드가 계산하는 방식대로 계산되므로, 테스트가 구조적으로 통과합니다. 기대값은 다른 곳에서 와야 합니다. 알려진 정상 리터럴, 손으로 풀어 본 예시, 명세입니다. |
| 수평 슬라이싱 | 어떤 구현보다 먼저 한 묶음의 테스트가 반영되었습니다. |

목은 시스템 경계에서만 사용합니다. 외부 API, 시간, 무작위성, 때때로 파일 시스템이나 데이터베이스입니다. 자신의 모듈은 절대 목으로 대체하지 마십시오.

## 자주 묻는 질문

**왜 리팩터링하지 않습니까? 설명에는 "red-green-refactor"라고 되어 있습니다.**

리팩터링 단계는 제거되었지만 설명은 그렇지 않았기 때문입니다. 제거는 의도적이었습니다. 에이전트가 그 단계를 거의 하지 않았으며, 구현과 리뷰를 별도의 세션으로 유지하는 것이 더 잘 동작합니다. 결과가 교과서적으로 여전히 TDD로 간주되는지는 루프가 더 나은 코드를 만들어 내는지보다 덜 중요합니다. 트리거 문구와 본문의 불일치는 [issue #589](https://github.com/mattpocock/skills/issues/589)로 제출되었으며 아직 열려 있으므로, "red-green-refactor"는 계속 스킬을 실행하는 문구로 동작합니다. 얻게 되는 것은 red-green이며, 리팩터링은 [code-review](https://aihero.dev/skills-code-review)에서 이루어집니다.

**테스트 시임을 고르라고 했는데, 무엇을 골라야 할지 전혀 몰랐습니다.**

이것이 이 스킬에서 가장 많이 보고되는 마찰입니다([issue #607](https://github.com/mattpocock/skills/issues/607)). 프롬프트는 후보 시임을 이름으로만 나열하며, 각각이 무엇을 잡아내고 무엇을 놓치는지에 대해서는 아무것도 말하지 않으므로, 라벨 사이에서 고르게 됩니다. 아직 배포된 수정은 없습니다. 실질적인 우회책은 답하기 전에 에이전트에게 트레이드오프를 묻는 것입니다. 통합 시임이 잡아내는 것 중 컴포넌트 수준 시임이 놓치는 것은 무엇이며, 얼마나 더 느린가? 이것이 연쇄가 하나의 프롬프트가 아니라 기능 전체를 시야에 둔 `to-spec`에서 미리 시임을 합의하는 이유이기도 합니다.

**스킬은 red가 먼저라고 하는데, 테스트보다 구현을 먼저 작성했습니다.**

그런 일이 일어납니다. 한 사용자가 [모델](https://www.aihero.dev/ai-coding-dictionary/model)을 다그쳤더니 이례적으로 솔직한 답을 얻었습니다. "스킬이 '한 번에 하나의 테스트, 올바른 이유로 실패하는 것을 지켜보라'고 한 것을 알고 있었습니다. 읽었습니다. 그냥 평소 습관대로 했습니다." 스킬은 이를 받아들입니다. 어떤 지시도 에이전트가 100% 따르게 만들지는 못하며, 더 엄격한 문구는 적은 이득을 위해 에이전트의 창의성을 제한합니다. 에이전트가 엄격하게 따르지 않더라도 루프를 실행할 가치가 있습니다. 결과가 전반적으로 여전히 더 낫기 때문입니다. 특정 슬라이스에서 엄격한 준수가 중요하다면, 스킬이 그것을 강제하리라고 믿지 말고 실행을 지켜보십시오.

**브라우저 테스트나 종단 간 테스트를 먼저 작성해야 합니까?**

대개 아니며, 스킬이 그것을 막지는 않습니다. 한 사용자는 에이전트가 Playwright 테스트를 먼저 작성한 다음, 긴 루프에서 그것을 다시 실행하다가 아직 존재하지도 않는 기능에 대해 *테스트*가 망가졌다고 결론 내렸다고 보고했습니다. 브라우저 테스트는 충분히 느려서 red-green 피드백 루프가 제값을 하지 못하게 됩니다. 저장소의 `CLAUDE.md`에 브라우저 테스트는 동작이 작동한 후에 온다고 명시하십시오.

**`/tdd`가 `/implement`나 강좌의 `/do-work`를 대체합니까?**

아니요. `/tdd`는 방법론을 문서화합니다. `/implement`는 단순한 작업→피드백→커밋 루프이며 `/do-work`의 직접적인 대체입니다. 강좌의 단일 `/do-work` 단계는 이제 `/implement`, `/tdd`, `/code-review`로 나뉩니다. 티켓에 대해 어느 것을 실행할지 묻는다면, 답은 거의 항상 `/implement`입니다.

**깊은 모듈과 인터페이스 설계 지침은 어디로 갔습니까?**

v1.0에서 [codebase-design](https://aihero.dev/skills-codebase-design)으로 옮겨졌으며, 여러 스킬이 하나의 어휘를 공유하도록 일반화되었습니다. `refactoring.md`도 같은 시기에 빠졌습니다. 리팩터링은 이제 [code-review](https://aihero.dev/skills-code-review)의 일이며, 그 스킬이 Fowler 코드 스멜 기준선을 담고 있습니다.

**다른 티켓에 대해 압니까?**

아니요. 하나의 티켓에 대해 실행하면, 이슈 그래프의 나머지를 볼 수 없으므로 형제 티켓에 속하는 작업을 제안할 수 있습니다([issue #129](https://github.com/mattpocock/skills/issues/129)). 이것은 `tdd`의 일이 아닙니다. 티켓과 함께 명세를 전달하면 도움이 되며, 애초에 티켓의 크기를 적절히 정하는 것이 더 도움이 됩니다.

## 제대로 동작하고 있다면

- 테스트 파일이 존재하기 전에, 멈추고 테스트하려는 시임을 명시하며 기다립니다.
- 테스트 묶음 다음에 코드 묶음이 오는 것이 아니라, 하나의 테스트가 나타나 red가 되고, 통과할 만큼의 코드를 받은 다음에야 다음 테스트가 나타납니다.
- 테스트 이름이 내부("checkout calls paymentService.process")가 아니라 능력("user can checkout with valid cart")으로 읽힙니다.
- 단언의 기대값이 코드가 계산하는 방식대로 다시 계산된 값이 아니라, 명세까지 추적할 수 있는 리터럴입니다.
- 내부 함수의 이름을 바꿔도 스위트의 어떤 것도 깨지지 않습니다.
- 목은 외부 경계(결제 API, 시계)에서만 나타나며, 자신의 모듈 주위에는 결코 나타나지 않습니다.

## 어디에 위치하는가

`tdd`는 주 연쇄의 구현 단계 안에서 실행되며, 그 자체로 하나의 단계가 아닙니다.

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

[to-spec](https://aihero.dev/skills-to-spec)이 테스트 시임을 미리 합의하고, [implement](https://aihero.dev/skills-implement)가 티켓마다 `tdd`를 진행하며, [code-review](https://aihero.dev/skills-code-review)가 이후 합의된 시임만 사용되었는지 확인하고 `tdd`가 더 이상 하지 않는 리팩터링을 맡습니다. 다른 이웃은 `tdd`가 사용하는 시임과 깊은 모듈 어휘의 공유 출처인 [codebase-design](https://aihero.dev/skills-codebase-design)입니다. 구현할 구체적인 동작이 있고 전체 명세가 없을 때는 언제든 단독으로 사용할 수도 있습니다. 어떤 스킬이 상황에 맞는지 확실하지 않다면, [ask-matt](https://aihero.dev/skills-ask-matt)가 안내합니다.
