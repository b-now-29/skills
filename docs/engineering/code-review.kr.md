## 하는 일

`code-review`는 `HEAD`와 사용자가 지정한 고정된 시점(커밋, 브랜치, 태그, `main`, `HEAD~5`) 사이의 diff를 두 축으로 리뷰합니다. **Standards**는 코드가 이 저장소의 코드 작성 방식을 따르는지 묻습니다. **Spec**은 코드가 원래의 이슈나 [명세](https://www.aihero.dev/ai-coding-dictionary/spec)가 요청한 것을 하는지 묻습니다. 각 축은 자체 [서브에이전트](https://www.aihero.dev/ai-coding-dictionary/subagent)에서 실행되므로, 어느 쪽도 다른 쪽의 추론을 보지 않습니다.

스킬은 두 축을 결코 병합하거나 순위를 다시 매기지 않습니다. 보고서는 *축별로* 가장 심각한 문제로 끝나며, 축을 넘나드는 단일 승자를 명시하기를 거부합니다. 변경은 한 축을 통과하고 다른 축에서 실패할 수 있습니다. 모든 관례를 따르지만 잘못된 것을 구현한 코드는 Standards를 통과하고 Spec에서 실패합니다. [티켓](https://www.aihero.dev/ai-coding-dictionary/ticket)이 요청한 것을 정확히 하지만 저장소의 관례를 깨는 코드는 그 반대입니다. 섞인 판정은 통과한 축이 실패한 축을 가리게 만듭니다.

## 언제 사용하는가

`/code-review`를 입력하거나, 브랜치, PR, 진행 중인 작업, 또는 "X 이후의" 무엇이든 리뷰해 달라고 요청하면 에이전트가 자동으로 사용합니다.

| 상황 | 사용할 것 |
| --- | --- |
| diff가 존재하며, 그것이 올바르게 만들어졌는지 *그리고* 올바른 것인지 알고 싶음 | `code-review` |
| diff에서 버그를 찾고 싶음: null 경로, 경쟁 상태, off-by-one | 이것이 아니라 Claude Code 자체의 내장 리뷰(아래의 이름 충돌 참조) |
| 아직 아무것도 작성되지 않았으며, 테스트 우선으로 작성하고 싶음 | [tdd](https://aihero.dev/skills-tdd) |
| 리뷰를 포함하여 명세 전체를 구현해야 함 | 이 스킬을 직접 호출하는 [implement](https://aihero.dev/skills-implement) |
| 하나의 diff가 아니라 코드베이스 전체가 표류함 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) |
| 무언가 망가졌는데 이유를 모름 | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |

고정된 시점은 사용자가 제공해야 합니다. 제공하지 않으면, 스킬은 추측하는 대신 물어봅니다. 무엇이든 생성하기 전에, 참조가 해석되는지와 diff가 비어 있지 않은지 확인하므로, 잘못 입력한 브랜치 이름은 두 개의 서브에이전트 내부가 아니라 사용자 앞에서 실패합니다.

## 사전 요구 사항

Standards 축은 아무것도 필요로 하지 않습니다. 저장소가 문서화한 것(`CODING_STANDARDS.md`, `CONTRIBUTING.md` 등)을 무엇이든 읽으며, 저장소가 아무것도 문서화하지 않았다면 내장 기준선을 사용합니다.

Spec 축은 명세가 존재하며 찾을 수 있어야 합니다. 다음 순서로 찾습니다.

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67`). 트래커 문서를 통해 가져옵니다.
2. 사용자가 인수로 전달한 경로.
3. 브랜치나 기능 이름과 일치하는 `docs/`, `specs/`, `.scratch/` 아래의 명세 파일.
4. 사용자에게 묻기.

1단계는 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills)가 작성하는 트래커 문서에 의존합니다. 그것이 없더라도 경로를 건네주면 축은 여전히 동작합니다. 명세가 전혀 없다면, 스킬은 Spec 서브에이전트를 건너뛰며, 보고서는 요구 사항을 지어내는 대신 "사용 가능한 명세 없음"이라고 말합니다.

## 두 축

| | Standards | Spec |
| --- | --- | --- |
| 질문 | 올바르게 만들어졌는가? | 올바른 것인가? |
| 읽는 것 | 저장소의 문서화된 표준, 그리고 코드 스멜 기준선 | 원래의 이슈나 명세 |
| 보고하는 것 | 문서화된 위반(엄격할 수 있음), 그리고 스멜(항상 판단의 문제) | 누락되었거나 부분적인 요구 사항, 범위 확장, 잘못 구현된 요구 사항 |
| 모든 발견 사항이 인용하는 것 | 표준 파일과 규칙, 또는 명명된 스멜과 해당 hunk | 명세의 해당 줄 |

이 설계는 사용자의 표준을 모르는 범용 리뷰 스킬을 피하기 위해 존재합니다. 그런 스킬은 코드베이스에서 의도적인 것을 지적하고, 코드베이스가 의존하는 불변 조건은 놓칩니다. 그래서 Standards 축에서는 저장소 자체의 문서가 [1차 자료](https://www.aihero.dev/ai-coding-dictionary/primary-source)이며, **저장소가 항상 우선합니다**.

**코드 스멜 기준선(smell baseline)**은 저장소의 표준 아래에 있습니다. Fowler의 _Refactoring_ 3장에서 가져온 열두 가지 코드 스멜입니다. Mysterious Name, Duplicated Code, Feature Envy, Data Clumps, Primitive Obsession, Repeated Switches, Shotgun Surgery, Divergent Change, Speculative Generality, Message Chains, Middle Man, Refused Bequest입니다. 각각은 라벨이 붙은 휴리스틱("Feature Envy 가능성")이며, 결코 엄격한 위반이 아닙니다. 각각은 스멜이 무엇이며 어떻게 고치는지를 명시하므로, 발견 사항은 불평만이 아니라 해결책과 함께 옵니다. 두 축 모두 린터가 이미 강제하는 것은 건너뜁니다.

## 자주 묻는 질문

**Claude Code 자체의 `/code-review`와 충돌합니다. 어떻게 해야 합니까?**

이것이 이 스킬에서 가장 많이 보고되는 문제이며, 수정되지 않았습니다. Claude Code는 자체 `/code-review`를 제공하는데, 그것은 다른 일을 합니다. diff에서 버그를 찾는 반면, 이 스킬은 명세 준수와 저장소 표준을 확인합니다. 이 라이브러리를 설치하면 둘 중 하나가 이기며, 어느 쪽이 이기는지는 설치 방법에 따라 다릅니다.

- **플러그인 마켓플레이스.** 모든 스킬이 `mattpocock-skills:` 접두사를 받으며, 내장 스킬은 접두사 없는 이름으로는 도달하기 어려워집니다.
- **일반 스킬 설치.** 로컬 파일이 이기며, 이 스킬이 내장 스킬을 가립니다.

한 가지 답은 Claude Code의 내장 스킬을 완전히 제거하는 것입니다. 그러면 [컨텍스트](https://www.aihero.dev/ai-coding-dictionary/context)가 많이 절약되며, 충돌은 문제가 되지 않습니다. 가려지는 현상 자체는 아마도 Claude Code [하네스](https://www.aihero.dev/ai-coding-dictionary/harness)의 버그일 것이므로(스킬 작성자는 스킬에 어떤 이름이든 붙일 수 있어야 합니다), 다른 답은 로컬 사본의 이름을 바꾸는 것입니다. `npx skills update`는 프런트매터 편집이나 디렉터리 이름 변경을 되돌립니다. 사용자들이 보고하는 지속적인 우회책은 스킬을 새 이름으로 포크하고 관리되는 세트에서 `code-review`를 빼는 것입니다. 수동으로 다시 동기화할 수 있도록 포크한 커밋을 기록해 두십시오.

**서브에이전트들이 계속 `/code-review`를 다시 호출하며 더 많은 에이전트를 생성합니다.**

이것은 알려진 열린 버그입니다. 여러 사람이 둘 이상의 하네스에서 이를 재현했습니다. Standards와 Spec 프롬프트가 위임을 금지하지 않으므로, 서브에이전트가 스킬을 다시 찾아 다시 확산할 수 있습니다. 한 보고서는 50개가 넘는 에이전트에 도달했습니다. 사람들이 포크에 적용한 해결책은 두 서브에이전트 지시서에 덧붙이는 한 줄입니다. "`/code-review`를 호출하거나 추가 에이전트를 생성하지 마라. 이 리뷰를 직접 수행하라." 일부는 모든 스킬이 그 방어 장치를 상속하도록 하네스 수준에서 처리하기를 선호합니다. 둘 다 아직 배포된 스킬에는 없습니다. 무인으로 실행한다면, 에이전트 수를 지켜보십시오.

**코드를 작성한 같은 [세션](https://www.aihero.dev/ai-coding-dictionary/session)에서 실행해야 합니까?**

새 세션을 선호하십시오. 한 독자의 말처럼 "같은 컨텍스트가 자신을 리뷰하는 것은 리뷰가 아니라 슬래시 명령이 붙은 확증 편향이다." 작성 세션에서 리뷰하는 에이전트는 코드를 형성한 모든 가정을 컨텍스트에 가지고 있습니다. 독립적인 리뷰어라면 그 컨텍스트를 가지지 않을 것입니다. 이것이 사람들이 내장 리뷰 단계가 없는 [implement](https://aihero.dev/skills-implement)를 요청하는 이유이기도 합니다. 그 단계는 방금 diff를 작성한 세션 안에서 리뷰를 실행하기 때문입니다. 독립적인 버전은 깨끗한 세션에서 직접 `/code-review`를 호출하는 것입니다.

**매 티켓 후입니까, 아니면 마지막에 한 번입니까?**

둘 다 동작하며, 스킬이 대신 결정하지 않습니다. 티켓마다 하면 각 diff가 Spec 축이 대조할 하나의 명확한 명세를 가질 만큼 작게 유지되며, 이것이 `implement`가 사용하는 방식입니다. 브랜치 끝에 일괄로 하면 티켓별 리뷰가 각각 놓치는 티켓 간의 상호 작용을 잡아냅니다. 확실하지 않다면, 티켓마다 리뷰하고 분기 지점을 기준으로 마지막에 한 번 더 실행하십시오.

**발견 사항을 신뢰할 수 있습니까?**

확인하지 않고는 아닙니다. 서브에이전트의 출력은 증거가 아니라 가설입니다. 한 팀은 산문 기반 리뷰가 놓쳤던 열두 개의 호환성 파괴 변경을 보고했습니다. 스킬은 두 보고서를 그대로 또는 가볍게 정리하여 결합합니다. 각 주장을 파일과 대조하여 다시 검증하지 않으므로, 발견 사항이 잘못된 위치를 인용하거나 영향을 과장할 수 있습니다. 조치하기 전에 각 발견 사항의 인용을 읽으십시오. 스킬은 모든 발견 사항이 인용(표준 규칙, 스멜과 그 hunk, 또는 명세의 줄)을 담도록 요구하며, 그것이 발견 사항을 확인 가능하게 만드는 것입니다.

**왜 실행할 때마다 새로운 문제를 찾습니까?**

각 수정이 리뷰할 새 코드를 추가하며, Standards 축의 판단의 문제 절반은 실행마다 다른 결과를 냅니다. 한 독자는 그 루프를 이렇게 설명했습니다. "/code-review와 /improve-code-architecture는 매번 새로운 것을 찾는다. 수정을 구현하고, 이 스킬들을 다시 실행하고, 계속 반복한다." 수렴 보장은 없습니다. 한 번의 리뷰를 단서 목록으로 취급하십시오. 인용된 규칙이 뒷받침하는 것에 조치한 다음, 멈추십시오. 깨끗하게 나올 때까지 루프로 실행하지 마십시오. 결코 그렇게 되지 않을 것입니다.

**커밋하지 않은 작업도 리뷰합니까?**

아니요. `<fixed-point>...HEAD`의 diff를 봅니다. 세 개의 점 형태는 merge-base부터 측정하며 스테이징된 변경과 작업 트리 변경을 제외합니다. `implement`가 중간 커밋을 만들지 않았다면, 리뷰는 다음 커밋에 들어갈 작업을 볼 수 없습니다. 먼저 커밋하고, 그다음 리뷰하고, 그다음 amend하거나 fixup을 추가하십시오.

## 제대로 동작하고 있다면

- 어떤 서브에이전트도 생성되기 전에, 잘못된 참조나 빈 diff에서는 시작을 거부합니다.
- 보고서가 하나의 병합된 목록이 아니라 `## Standards`와 `## Spec` 아래의 두 개의 별도 블록으로 도착합니다.
- 모든 Standards 발견 사항이 저장소 파일 중 하나의 규칙이나 열두 가지 스멜 중 하나를 명시하며 hunk를 인용합니다. 모든 Spec 발견 사항은 명세의 한 줄을 인용합니다.
- 마무리 요약이 축별로 가장 심각한 문제를 제시하며, 전체 승자를 고르기를 거부합니다.
- 사용 가능한 명세가 없을 때, Spec 블록은 코드에서 추론한 요구 사항을 나열하는 대신 그렇다고 말합니다.

## 어디에 위치하는가

`code-review`는 구현 연쇄의 끝부분 근처에 있는 리뷰 단계입니다: `grill-with-docs → to-spec → to-tickets → implement → code-review → retro`. 가리키는 어떤 브랜치나 PR에 대해서도 단독으로 사용할 수 있습니다.

- [implement](https://aihero.dev/skills-implement)가 가장 가까운 이웃입니다. 구현을 진행하고, 커밋하기 전에 자체 마무리 리뷰로 이 스킬을 호출합니다. [implement-spec](https://aihero.dev/skills-implement-spec)은 통합 브랜치 전체에 대해 한 번 같은 일을 합니다.
- [retro](https://aihero.dev/skills-retro)가 그 뒤에 오며 이 스킬을 조정합니다. 세션에서 리뷰가 어떤 부류의 실수를 놓치는 것이 드러나면, `retro`가 Standards 축이 이후 읽게 될 검사나 `CODING_STANDARDS.md` 규칙을 제안합니다.
- [pr](https://aihero.dev/skills-pr)은 리뷰된 작업이 올라가면 풀 리퀘스트 본문을 작성합니다.
- [to-spec](https://aihero.dev/skills-to-spec)과 [to-tickets](https://aihero.dev/skills-to-tickets)가 Spec 축이 대조하는 문서를 만들어 내므로, 모호한 명세는 그 축을 모호하게 만듭니다.
- [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)는 코드베이스 전체에 대한 대응 스킬입니다. 이 스킬은 하나의 diff만 보기 때문입니다.

상황에 어떤 스킬이 필요한지 확실하지 않을 때는 [ask-matt](https://aihero.dev/skills-ask-matt)가 세트 전체에 걸쳐 안내합니다.
