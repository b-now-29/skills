## 하는 일

`implement-spec`은 [명세](https://www.aihero.dev/ai-coding-dictionary/spec)와 그 [티켓](https://www.aihero.dev/ai-coding-dictionary/ticket)을 받아 전체를 한 번의 실행으로 반영합니다. 조율하는 [에이전트](https://www.aihero.dev/ai-coding-dictionary/agent)가 각 티켓을 자체 git 워크트리에서 작업하는 구현자 [서브에이전트](https://www.aihero.dev/ai-coding-dictionary/subagent)에게 건네고, 완료된 각 브랜치를 하나의 **통합 브랜치(integration branch)**에 병합하며, 결과에 대해 [code-review](https://aihero.dev/skills-code-review)를 실행하고, 티켓을 해결합니다.

티켓을 목록이 아니라 **작업 그래프(task graph)**로 읽습니다. 차단 관계가 무엇을 시작할 수 있는지 결정하므로, 어느 순간이든 차단하는 티켓이 모두 반영된 티켓들의 **전선(frontier)**이 있으며, 전선의 모든 티켓이 동시에 실행됩니다. 그것이 티켓을 하나씩 처리하는 것과의 차이입니다. 속도를 정하는 것은 트래커에서의 티켓 순서가 아니라 그래프의 형태입니다.

## 언제 사용하는가

`/implement-spec`을 입력하여 호출하며, 에이전트가 스스로 사용하지는 않습니다.

| 상황 | 사용할 것 |
| --- | --- |
| 차단 관계가 있는 티켓으로 분할된 명세를 한 번의 실행으로 반영하고 싶음 | `/implement-spec` |
| 자신의 [컨텍스트 윈도우](https://www.aihero.dev/ai-coding-dictionary/context-window)에서 한 번에 하나의 티켓씩, 티켓 사이에 [비우면서](https://www.aihero.dev/ai-coding-dictionary/clearing) | [implement](https://aihero.dev/skills-implement) |
| 아직 티켓으로 분할되지 않은 명세 | 먼저 [to-tickets](https://aihero.dev/skills-to-tickets) |
| 실질적인 그래프가 없는 작은 작업 | 바로 [implement](https://aihero.dev/skills-implement) |

## 사전 요구 사항

- **이슈 트래커.** 스킬은 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills)가 구성한 트래커에서 티켓을 읽고, 그곳에서 해결합니다. 구성된 것이 없다면 추측하는 대신 멈추고 먼저 그것을 실행하라고 안내합니다.
- [to-tickets](https://aihero.dev/skills-to-tickets)가 작성하는 것과 같은 **차단 관계를 가진 티켓**. 관계가 없으면 그래프가 평평해지고 모든 티켓이 한꺼번에 시작됩니다.
- **서브에이전트를 백그라운드에서 실행하고 각각에 git 워크트리를 주는 [하네스](https://www.aihero.dev/ai-coding-dictionary/harness).** 이 스킬은 티켓을 동시에 실행하기 위해 존재하므로, 서브에이전트를 한 번에 하나씩 실행하는 하네스에서는 그저 더 느린 `implement`일 뿐입니다.

## 통합 브랜치

모든 것이 하나의 브랜치에 반영됩니다. 각 구현자는 다음을 수행합니다.

1. 시작하기 전에 워크트리가 통합 브랜치를 기반으로 하는지 확인하고,
2. [tdd](https://aihero.dev/skills-tdd)로 한 번에 하나의 슬라이스씩 red-green으로 티켓을 구현하며,
3. 완료를 보고하기 전에 통합 브랜치의 최신 커밋을 자신의 브랜치에 병합하여, 반영이 fast-forward가 되도록 합니다.

풀 리퀘스트가 존재할지 여부는 트래커가 결정합니다. 트래커가 PR을 통해 작업을 종료하거나 사용자가 요청하면, 스킬은 첫 번째 병합 후 초안 PR을 열고 마지막에 준비 완료로 표시합니다. 그렇지 않으면 실행은 모든 티켓이 트래커의 종료 방식대로 해결된 채 통합 브랜치에서 멈추며, 이는 로컬 마크다운 트래커에 대해 완전히 오프라인으로 동작합니다.

구현자는 붙여 넣은 요약이 아니라 [컨텍스트 포인터](https://www.aihero.dev/ai-coding-dictionary/context-pointer)(명세, 티켓, 공유 탐색 노트, 이전 커밋)를 통해 오케스트레이터와 소통합니다. 이렇게 하면 각 서브에이전트의 프롬프트가 작게 유지되고, 오케스트레이터의 윈도우에 그래프를 위한 공간이 남습니다.

## 자주 묻는 질문

**각 티켓에 직접 `/implement`를 실행하는 것과 어떻게 다릅니까?**

이것이 이 스킬이 답하기 위해 존재하는 질문입니다. 이 스킬이 배포되기 전에 사람들은 계속 자신만의 버전을 만들었으며, 한 사용자는 그 필요를 이렇게 설명했습니다. "명세에 티켓이 5개 넘게 있을 수 있는데, 일일이 새 세션을 만들어 티켓을 하나씩 구현하라고 지시하는" 대신 "서브에이전트가 티켓을 구현하기"를 원했습니다. `implement`에서는 사용자가 디스패처입니다. 티켓당 하나의 [세션](https://www.aihero.dev/ai-coding-dictionary/session)을 열고, 그 사이에 비우고, 어떤 티켓의 차단이 풀렸는지 직접 추적합니다. `implement-spec`은 그 일을 하나의 조율 세션에 넘깁니다. 그 대가는 더 이상 각 티켓의 작업이 반영될 때 읽지 않고, 마지막에 통합 브랜치를 리뷰한다는 것입니다. 실행을 시작하려면 컨텍스트를 비우고 명세에 대한 포인터(이슈 번호 또는 파일 경로)와 함께 `/implement-spec`을 입력하십시오. 실질적인 그래프가 없는 작은 변경이라면 건너뛰고 바로 `implement`를 사용하십시오.

**GitHub가 필요합니까? 브랜치에서 멈추기를 원합니다.**

이제는 아닙니다. 진행 중 버전을 좋아했던 한 사용자는 정확히 이런 불만을 가졌습니다. "마지막에 PR을 만드는데, 그러려면 GitHub 같은 온라인 저장소가 필요하다. 같은 작업을 오프라인으로 하고 모든 작업이 병합된 브랜치에서 멈출 수 있으면 좋겠다." 실행은 이제 통합 브랜치에서 끝납니다. PR은 구성된 트래커가 PR을 통해 작업을 종료하거나 사용자가 요청할 때만 열리므로, 로컬 마크다운 트래커에서는 모든 티켓이 해결되고 작업이 브랜치에 병합된 채 실행이 끝납니다.

**리뷰와 수정 루프가 몇 시간 동안 실행되거나, 아직 구현되지 않은 티켓을 계속 "수정"했습니다.**

둘 다 스킬이 지정한 단 하나의 지점이 아닌 곳에서 `code-review`가 실행될 때 일어납니다. 코드를 명세 전체와 비교하므로, 모든 티켓이 반영된 후에만 의미가 있습니다. 실행 도중에 실행되면, 구현되지 않은 모든 티켓이 실패로 읽힙니다. 그러면 에이전트가 그 티켓을 구현하고, 그것이 또 다른 리뷰를 촉발합니다. 마지막에 스킬은 `code-review`를 한 번 실행하고 모든 발견 사항을 하나의 수정 서브에이전트에 보내지만, 그 수정 후에 언제 멈출지는 아직 말하지 않습니다. 한 사용자는 티켓 다섯 개짜리 기능에서 "리뷰와 수정 루프가 약 네 시간 걸렸다"고 보고했습니다. 두 번째 광범위한 리뷰가 시작되는 것을 보면, 수정된 발견 사항에 대한 집중된 검사를 실행하고 멈추라고 지시하십시오. 첫 번째 리뷰가 실제 문제를 찾을 것으로 예상하십시오. 실행의 출력은 그 자체로 출시할 것이 아니라 리뷰가 완성하는 초안입니다.

**implement처럼 tdd를 진행합니까?**

이제는 그렇지만, 처음에는 아니었습니다. 진행 중 버전을 실행한 사용자들은 "구현자 서브에이전트가 /tdd 지시를 상속하지 않는다"는 것을 알아챘으며, 그래서 하나의 티켓에서 명세 전체로 규모를 키우자마자 red-green이 멈췄습니다. 이제 각 구현자는 `tdd`로 티켓을 구현합니다. `implement` 세션에서처럼 대화형으로 시임을 합의하는 단계는 여전히 없으므로, 시임을 고정하고 싶다면 명세나 티켓에 명시하십시오.

**병렬로 실행된 두 구현자가 같은 파일에서 충돌하거나, 같은 것에 다른 이름을 붙였습니다.**

워크트리는 충돌을 없애는 것이 아니라 병합 시점으로 미룹니다. 티켓 텍스트로 작성된 차단 관계는 각 티켓이 어떤 파일을 건드릴지에 대한 추측이며, "코드베이스의 다른 부분"에 있는 두 티켓도 여전히 메시지 카탈로그, 구성 레지스트리, 또는 타입을 공유합니다. 각 구현자는 자신의 티켓과 공유 노트만 볼 뿐 다른 구현자의 진행 중인 작업은 보지 못하므로, 한 사용자의 웹 티켓과 모바일 티켓은 같은 문자열을 각각 `blockedSince`와 `blockedOn`으로 추가했습니다. 두 전선 티켓이 하나의 공유 파일을 건드린다면, 둘 사이에 차단 관계를 추가하여 차례로 실행되게 하거나, 탐색 노트에서 각 티켓이 추가하는 정확한 이름을 고정하십시오.

**차단 티켓이 병합된 후에도 차단된 티켓이 시작되지 않습니다.**

이것은 GitHub에서 알려진 문제입니다. 트래커의 차단 개수는 차단 티켓이 *종료*될 때만 줄어들며, 티켓은 대개 PR이 병합될 때, 즉 실행이 끝날 때 종료됩니다. 트래커는 시작 그래프의 올바른 출처이지만 실행 도중에는 낡은 출처입니다. 오케스트레이터에게 어떤 티켓이 통합 브랜치에 병합되었는지 직접 추적하고 그것으로 전선을 계산하라고 지시하십시오.

**이것이 Sandcastle이나 AFK 스크립트를 대체합니까?**

아니요. 스킬이 이제 구현까지 다루기 때문에 사람들이 묻습니다. "Sandcastle이 아직도 의미가 있는가? 이제 스킬이 구현도 처리할 수 있는 것 같다." `implement-spec`은 하나의 하네스 세션 안에서 에이전트가 조율을 맡게 하며, 인프라가 필요 없고 지켜보며 방향을 잡을 수 있습니다. 진정으로 [AFK](https://www.aihero.dev/ai-coding-dictionary/afk)인 작업에는 결정적인 루프([Sandcastle](https://github.com/mattpocock/sandcastle), 셸 스크립트, CI 작업)가 더 빠르고, 저렴하며, 안정적입니다. 어떤 에이전트도 조율 결정을 내리지 않기 때문입니다.

**티켓의 핵심 테스트가 워크트리 안에서 건너뛰어졌는데, green으로 보고되었습니다.**

워크트리는 git이 추적하는 것만 담습니다. gitignore된 픽스처, 로컬 데이터베이스, 자격 증명을 읽는 테스트는 그곳에서 조용히 건너뛰어질 수 있습니다. 검증이 추적되지 않는 자료에 의존하는 티켓은 대신 메인 체크아웃에서 실행하라고 오케스트레이터에게 지시하십시오.

## 제대로 동작하고 있다면

- 그래프가 허락할 때마다 여러 구현자가 차례로가 아니라 동시에 실행되고 있습니다.
- 티켓은 실행 전체가 끝날 때가 아니라, 마지막 차단 티켓이 통합 브랜치에 반영되는 즉시 시작됩니다.
- 모든 티켓의 기록에 `tdd`가 실행되어, 코드보다 실패하는 테스트가 먼저 있습니다.
- 통합 브랜치로의 병합이 충돌 해결이 아니라 fast-forward입니다.
- 실행이 모든 티켓이 해결된 하나의 브랜치에서 끝나며, 트래커가 원할 때만 PR이 있습니다.

## 어디에 위치하는가

`implement-spec`은 주 연쇄의 구현 단계로, 티켓마다 한 번씩 [implement](https://aihero.dev/skills-implement)를 실행하는 것의 병렬 대안입니다.

```txt
grill-with-docs → to-spec → to-tickets → implement-spec → retro
```

이웃은 이 스킬이 작업 그래프로 읽는 차단 관계를 선언하는 [to-tickets](https://aihero.dev/skills-to-tickets)와, 마무리하기 전에 통합 브랜치에 대해 실행하는 [code-review](https://aihero.dev/skills-code-review)입니다. 어떤 흐름에 있는지 확실하지 않을 때는 [ask-matt](https://aihero.dev/skills-ask-matt)가 세트 전체에 대한 라우터입니다.
