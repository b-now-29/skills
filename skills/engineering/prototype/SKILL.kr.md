# 프로토타입

프로토타입은 **질문에 답하는 일회용 코드**입니다. 질문이 형태를 결정합니다.

## 분기 선택

사용자의 프롬프트, 주변 코드를 사용하거나, 사용자가 있다면 물어봄으로써 어떤 질문에 답하고 있는지 파악하십시오.

- **"이 로직 / 상태 모델이 적절하게 느껴지는가?"** → [LOGIC.md](LOGIC.md). 문서상으로는 추론하기 어려운 사례를 통해 상태 기계를 밀어붙이며, 개발자가 아닌 사람도 조작할 수 있는 하나의 공유 가능한 HTML 파일(자유 조작 버튼과 탭으로 구분된 안내형 시연)을 만듭니다.
- **"이것은 어떻게 보여야 하는가?"** → [UI.md](UI.md). URL 검색 매개변수와 떠 있는 하단 바로 전환할 수 있는, 근본적으로 다른 여러 UI 변형을 하나의 라우트에 생성합니다.

두 분기는 매우 다른 산출물을 만들어 내므로, 이를 잘못 판단하면 프로토타입 전체가 낭비됩니다. 질문이 진정으로 모호하고 사용자에게 연락할 수 없다면, 주변 코드에 더 잘 맞는 분기(백엔드 모듈 → 로직, 페이지나 컴포넌트 → UI)를 기본으로 선택하고 프로토타입 상단에 그 가정을 명시하십시오.

## 양쪽 모두에 적용되는 규칙

1. **첫날부터 일회용이며, 그렇게 명확히 표시됩니다.** 맥락이 명확하도록 프로토타입 코드를 실제로 사용될 곳 가까이(프로토타이핑 대상인 모듈이나 페이지 옆)에 두되, 무심코 읽는 사람도 그것이 프로덕션이 아니라 프로토타입임을 알 수 있도록 이름을 지으십시오. 일회용 UI 라우트의 경우, 프로젝트가 이미 사용하는 라우팅 관례를 따르십시오. 새로운 최상위 구조를 만들어 내지 마십시오.
2. **실행이 간단해야 합니다.** UI 프로토타입은 프로젝트의 작업 실행기에서 하나의 명령으로 시작됩니다. `pnpm <name>`, `python <path>`, `bun <path>` 등입니다. 로직 데모는 사용자가 더블 클릭하는 하나의 HTML 파일입니다. 어느 쪽이든, 시작하는 데 생각이 필요 없어야 합니다.
3. **기본적으로 영속성이 없습니다.** 상태는 메모리에 존재합니다. 영속성은 프로토타입이 _확인하는_ 대상이지, 프로토타입이 의존해야 할 대상이 아닙니다. 질문이 명시적으로 데이터베이스를 포함한다면, 임시 DB나 "PROTOTYPE, wipe me"와 같은 명확한 이름을 가진 로컬 파일을 사용하십시오.
4. **다듬기는 건너뛰십시오.** 테스트도 없고, 프로토타입을 _실행 가능하게_ 만드는 것 이상의 오류 처리도 없으며, 추상화도 없습니다. 요점은 무언가를 빠르게 배우는 것입니다.
5. **상태를 드러내십시오.** 모든 액션 후(로직) 또는 모든 변형 전환 시(UI), 사용자가 무엇이 바뀌었는지 볼 수 있도록 관련된 전체 상태를 출력하거나 렌더링하십시오.
6. **끝나면 보존하십시오.** 검증된 결정을 실제 코드에 반영한 다음, 프로토타입 자체를 **1차 자료**로 보존하십시오. main 밖의 일회용 브랜치에 커밋하고, 구현 이슈에 그 브랜치를 가리키는 컨텍스트 포인터를 남기십시오. 답(판정과 그것이 해결한 질문)도 이슈나 커밋에 보존하십시오. main 브랜치에는 검증된 결정만 남깁니다.
