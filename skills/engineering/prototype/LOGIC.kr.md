# 로직 프로토타입

누구나 버튼을 클릭하여 상태 모델을 조작할 수 있게 해 주는 하나의 독립적인 HTML 파일(**공유 가능한 데모**)입니다. 질문이 **비즈니스 로직, 상태 전이, 또는 데이터 형태**에 관한 것일 때 사용하십시오. 문서상으로는 합리적으로 보이지만 실제 사례를 거쳐 보아야 비로소 잘못되었다고 느껴지는 종류의 것입니다.

설치할 것이 없는 하나의 파일이므로, 개발자가 아닌 사람(디자이너, PM, 도메인 전문가)에게 건네어 그들이 직접 모델을 체감하게 할 수 있습니다. 따라서 코드의 언어가 아니라 그들의 언어로 말해야 합니다.

## 이 형태가 적합한 경우

- "이 상태 기계가 X 다음에 Y가 오는 엣지 케이스를 처리하는지 잘 모르겠다."
- "이 데이터 모델로 정말 … 하는 경우를 표현할 수 있는가"
- "API를 작성하기 전에 어떤 모습이어야 할지 감을 잡고 싶다."
- 누군가가 **버튼을 누르고 상태가 바뀌는 것을 보고** 싶어 하는 모든 경우.

질문이 "이것은 어떻게 보여야 하는가"라면, 이것은 잘못된 분기입니다. [UI.md](UI.md)를 사용하십시오.

## 프로세스

### 1. 질문을 명시하십시오

코드를 작성하기 전에, 어떤 상태 모델과 어떤 질문을 프로토타이핑하는지 적으십시오. 데모 상단에 한 단락으로(주석만이 아니라 눈에 보이는 소개로) 작성하십시오. 잘못된 질문에 답하는 로직 프로토타입은 순수한 낭비이므로, 사용자가 지금 보고 있든 나중에 AFK 상태에서 돌아오든 확인할 수 있도록 질문을 명시적으로 만드십시오.

### 2. 로직을 이식 가능한 모듈로 격리하십시오

실제 로직(질문에 답하는 부분)을 하나의 `<script>` 블록에 넣되, 나중에 꺼내어 실제 코드베이스에 넣을 수 있는 작고 순수한 모듈로 작성하십시오. 그 주변의 페이지는 일회용이지만, 이 모듈은 그렇지 않습니다.

적절한 형태는 질문에 따라 다릅니다.

- **순수 리듀서**: `(state, action) => state`. 액션이 개별 이벤트이고 상태가 단일 값일 때 좋습니다.
- **상태 기계**: 명시적인 상태와 전이. "지금 어떤 액션이 허용되는가"가 질문의 일부일 때 좋습니다.
- 평범한 데이터 타입에 대한 **작은 순수 함수 집합**. 암묵적인 현재 상태 없이 변환만 있을 때 좋습니다.
- 로직이 진정으로 지속적인 내부 상태를 소유하는 경우, **명확한 메서드 표면을 가진 클래스나 모듈**.

페이지에 연결하기 가장 쉬운 형태가 *아니라*, 묻고 있는 질문에 가장 잘 맞는 형태를 선택하십시오. 순수하게 유지하십시오. DOM도, `document`도, 그 안으로 손을 뻗는 버튼 핸들러도 없어야 합니다. 페이지가 모듈을 호출하며, 반대 방향으로는 아무것도 흐르지 않습니다. 이것이 프로토타입을 그 수명 이후에도 유용하게 만드는 것입니다. 질문에 답이 나오면, 검증된 리듀서 / 상태 기계 / 함수 집합이 그 자체로 실제 모듈로 옮겨집니다.

### 3. 공유 가능한 HTML 파일을 만드십시오

하나의 파일, 평범한 HTML/CSS/JS로 작성합니다. 프레임워크도, 번들러도, 서버도 없으며, 더블 클릭으로 열리고 이메일로 주고받아도 문제가 없도록 모든 것을 인라인으로 넣습니다. 누구나 파일을 여는 것만으로 실행할 수 있어야 합니다.

개발자가 아닌 사람을 위해 작성하십시오. 모든 라벨은 코드가 아니라 **도메인 언어**로 되어 있습니다. 버튼과 상태는 리듀서가 아니라 비즈니스처럼 읽혀야 합니다. 무슨 일이 일어나고 있는지 평이한 말로 설명하십시오.

위에서 아래로, 깔끔한 계층 구조로 배치하십시오.

1. 이 데모로 무엇을 탐색할 수 있는지에 대한 **제목과 한 줄 설명**(1단계의 질문).
2. **현재 상태**: 관련된 전체 상태를 읽기 쉬운 패널(원시 JSON 덤프가 아니라 라벨이 붙은 필드)로 렌더링하며, 변경이 보이도록 매 클릭 후 다시 렌더링합니다. 개발자가 아닌 사람이 따라가는 데 도움이 된다면, 방금 무엇이 바뀌었는지 강조하십시오.
3. **자유 조작 버튼**: 액션당 하나의 버튼으로, 항상 사용 가능하므로 누구나 어떤 순서로든 모델을 건드려 볼 수 있습니다. 각 클릭은 해당 액션을 디스패치하고 상태를 다시 렌더링합니다.
4. **안내형 시연**: 탭당 하나씩 있는 **시나리오** 집합입니다. 각 탭에는 시나리오에 대한 짧은 평이한 언어의 설명(시나리오가 설정하는 상황과 주목할 점)이 있고, 그 아래에 해당 시나리오를 위해 **눌러야 할 버튼**이 순서대로 있습니다. 각 단계는 실제 버튼입니다. 클릭하면 해당 액션을 수행하고 다음 단계로 이동합니다. 시연을 시작하면 알려진 초기 상태로 재설정되므로, 시나리오는 매번 같은 방식으로 실행됩니다.

다루기 까다로운 경우, 즉 문서상으로 추론하기 어려운 경우를 보여 주는 시나리오를 선택하십시오. 정상 경로, 까다로운 엣지 케이스, 허용되어서는 안 되는 무언가에 대한 시도입니다.

아름답지만 절제되게 유지하십시오. 깔끔한 타이포그래피, 넉넉한 간격, 하나의 강조색. 애니메이션도, 장식도 없어야 합니다. 상태와 버튼과 경쟁하는 것은 아무것도 없어야 합니다.

### 4. 건네주십시오

파일을 보내거나, 대신 열어 주십시오. 그들은 시간이 날 때 시연과 자유 조작을 클릭해 볼 것입니다. 흥미로운 순간은 그들이 "잠깐, 이건 불가능해야 하는데" 또는 "어, X는 다를 거라고 생각했는데"라고 말할 때입니다. 그것이 바로 _아이디어_의 버그이며, 그것이 핵심입니다. 그들이 새로운 액션이나 새로운 시나리오를 원한다면 추가하십시오. 프로토타입은 진화합니다.

### 5. 답과 프로토타입을 보존하십시오

프로토타입이 질문에 답하면, 답을 보존한 다음 [SKILL](SKILL.md)이 기술하는 방식대로 프로토타입을 보존하십시오. 로직에 특화된 대응 관계는 다음과 같습니다. 검증된 리듀서 / 상태 기계 / 함수 집합은 실제 모듈로 옮겨지고(결정이 흡수됨), HTML 셸은 프로토타입을 1차 자료로 보관하는 일회용 브랜치로 함께 이동하며, 하나의 독립적인 파일이므로 그곳에서 언제든 손쉽게 다시 실행할 수 있습니다.

## 안티 패턴

- **테스트를 추가하지 마십시오.** 테스트가 필요한 프로토타입은 더 이상 프로토타입이 아닙니다.
- **실제 데이터베이스에 연결하지 마십시오.** 질문이 특별히 영속성에 관한 것이 아니라면 메모리 내 상태를 사용하십시오.
- **일반화하지 마십시오.** "나중에 X를 지원하고 싶다면"은 없습니다. 프로토타입은 하나의 질문에 답합니다.
- **로직과 페이지를 뒤섞지 마십시오.** 순수 모듈이 DOM, `document`, 또는 버튼 핸들러를 참조한다면, 더 이상 옮길 수 없습니다. 페이지를 순수 모듈 위의 얇은 셸로 유지하십시오.
- **프레임워크, 번들러, 서버를 찾지 마십시오.** 수신자가 더블 클릭하는 하나의 파일이어야 합니다. React 앱이나 개발 서버는 "공유 가능"을 무너뜨립니다.
- **HTML 셸을 프로덕션에 배포하지 마십시오.** 페이지는 손으로 클릭해 보는 용도로 최적화되어 있습니다. 그 뒤의 로직 모듈이 보존할 가치가 있는 부분입니다.
