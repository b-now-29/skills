# UI 프로토타입

떠 있는 하단 바로 전환할 수 있는, **근본적으로 다른 여러 UI 변형**을 하나의 라우트에 생성합니다. 사용자는 브라우저에서 변형들을 넘겨 보고, 하나를 선택하거나(또는 각각에서 일부를 가져오고), 나머지는 버립니다.

질문이 무언가가 어떻게 보이는지가 아니라 로직/상태에 관한 것이라면, 이것은 잘못된 분기입니다. [LOGIC.md](LOGIC.md)를 사용하십시오.

## 이 형태가 적합한 경우

- "이 페이지는 어떻게 보여야 하는가?"
- "결정하기 전에 이 대시보드에 대한 몇 가지 선택지를 보고 싶다."
- "설정 화면에 다른 레이아웃을 시도해 보라."
- 사용자가 그렇지 않으면 머릿속의 모호한 목업 세 개 중에서 고르느라 하루를 보낼 모든 경우.

## 두 가지 하위 형태: 하위 형태 A를 강력히 선호

UI 프로토타입은 **앱의 나머지 부분과 맞닿아 있을 때** 판단하기가 훨씬 쉽습니다. 실제 헤더, 실제 사이드바, 실제 데이터, 실제 밀도가 있을 때입니다. 그 자체로만 존재하는 일회용 라우트는 진공 상태입니다. 고립된 상태에서는 모든 변형이 괜찮아 보입니다. 변형을 호스팅할 그럴듯한 기존 페이지가 있다면 언제나 하위 형태 A를 기본으로 하십시오. 프로토타입에 진정으로 가까운 거처가 없을 때만 하위 형태 B를 사용하십시오.

### 하위 형태 A: 기존 페이지에 대한 조정 (선호)

라우트가 이미 존재합니다. 변형은 `?variant=` URL 검색 매개변수로 구분되어 **같은 라우트에** 렌더링됩니다. 기존의 데이터 가져오기, 매개변수, 인증은 모두 그대로 유지됩니다. 렌더링만 교체됩니다. 이것이 기본값입니다. 그러지 말아야 할 특별한 이유가 없다면 이것을 선택하십시오.

프로토타입 대상이 아직 페이지는 없지만 *자연스럽게 어떤 페이지 안에 들어갈* 것이라면(대시보드의 새 섹션, 설정 화면의 새 카드, 기존 흐름의 새 단계), 여전히 하위 형태 A입니다. 호스트 페이지 안에 변형을 마운트하십시오.

### 하위 형태 B: 새 페이지 (최후의 수단)

프로토타입 대상이 진정으로 들어갈 기존 페이지가 없는 경우에만 사용하십시오(예: 완전히 새로운 최상위 화면, 또는 어디에도 합리적으로 삽입할 수 없는 흐름).

프로젝트가 이미 사용하는 라우팅 관례를 따라 **일회용 라우트**를 생성하십시오. 새로운 최상위 구조를 만들어 내지 마십시오. 그것이 프로토타입임이 명백하도록 이름을 지으십시오(예: 경로나 파일 이름에 `prototype`이라는 단어를 포함). `?variant=` 패턴은 같습니다.

하위 형태 B로 결정하기 전에 확인하십시오. 이것을 삽입할 수 있는 기존 페이지가 정말 없습니까? 빈 라우트는 내용이 채워진 라우트라면 드러냈을 설계 문제를 숨깁니다.

두 하위 형태 모두에서 떠 있는 하단 바는 동일합니다.

## 프로세스

### 1. 질문을 명시하고 N을 선택하십시오

**3개의 변형**을 기본으로 하십시오. 5개를 넘으면 더 이상 근본적으로 다르지 않고 잡음이 되기 시작하므로, 거기서 상한을 두십시오.

계획을 한 줄로, 프로토타입의 위치나 파일 상단의 주석에 적으십시오.

> "기존 `/settings` 라우트에서 `?variant=`로 전환할 수 있는 설정 페이지의 세 가지 변형."

이는 사용자가 이의를 제기하기 위해 자리에 있든 없든 효과가 있습니다.

### 2. 근본적으로 다른 변형을 생성하십시오

각 변형의 초안을 작성하십시오. 각각은 다음을 지켜야 합니다.

- 페이지의 목적과 페이지가 접근할 수 있는 데이터.
- 프로젝트의 컴포넌트 라이브러리 / 스타일링 시스템(TailwindCSS, shadcn, MUI, 일반 CSS 등 무엇이든).
- 명확하게 내보내진 컴포넌트 이름. 예: `VariantA`, `VariantB`, `VariantC`.

변형은 **구조적으로 달라야** 합니다. 색상만 다른 것이 아니라 다른 레이아웃, 다른 정보 계층, 다른 주요 어포던스를 가져야 합니다. 약간씩 조정한 카드 그리드 세 개는 UI 프로토타입이 아니라 벽지입니다. 두 초안이 너무 비슷하게 나오면, 명시적으로 "카드 그리드를 사용하지 말라"는 지침과 함께 하나를 다시 만드십시오.

### 3. 함께 연결하십시오

라우트에 하나의 전환기 컴포넌트를 생성하십시오.

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

하위 형태 A(기존 페이지)의 경우: 기존의 모든 데이터 가져오기를 전환기 위에 유지하십시오. 렌더링되는 하위 트리만 변형마다 바뀝니다.

하위 형태 B(새 페이지)의 경우: `/prototype/<name>` 아래의 일회용 라우트가 같은 전환기를 마운트합니다.

### 4. 떠 있는 전환기를 만드십시오

화면 하단 중앙에 고정 위치로 배치되는 작은 바로, 세 부분으로 구성됩니다.

- **왼쪽 화살표**: 이전 변형으로 순환합니다(처음과 끝이 이어짐).
- **변형 라벨**: 현재 변형 키와, 변형이 이름을 내보낸다면 그 이름도 표시합니다. 예: `B (Sidebar layout)`.
- **오른쪽 화살표**: 앞으로 순환합니다(처음과 끝이 이어짐).

동작:

- 화살표를 클릭하면 URL 검색 매개변수가 업데이트되어(프레임워크의 라우터 사용. 예: Next의 `router.replace`, React Router의 `navigate` 등) 변형을 공유할 수 있고 새로 고침해도 유지됩니다.
- 키보드: `←`와 `→` 화살표 키로도 순환합니다. `<input>`, `<textarea>`, `[contenteditable]`에 포커스가 있을 때는 화살표 키를 가로채지 마십시오.
- 평가 대상인 디자인의 일부가 아님이 명백하도록, 페이지와 시각적으로 구별되게 하십시오(예: 고대비 알약 모양, 은은한 그림자).
- 프로덕션 빌드에서는 숨기십시오. 잘못 병합된 프로토타입이 바를 사용자에게 배포하지 않도록, `process.env.NODE_ENV !== 'production'` 또는 그에 상응하는 검사로 제한하십시오.

두 하위 형태가 모두 재사용할 수 있도록 전환기를 하나의 공유 컴포넌트에 두십시오. 프로젝트에서 공유 UI가 있는 곳에 배치하십시오.

### 5. 건네주십시오

URL(과 `?variant=` 키)을 알려 주십시오. 사용자는 시간이 날 때 넘겨 볼 것입니다. 흥미로운 피드백은 대개 **"B의 헤더와 C의 사이드바를 원한다"**이며, 그것이 사용자가 실제로 원하는 디자인입니다.

### 6. 답을 보존하고 정리하십시오

변형이 선택되면, 답(어떤 변형이며 그 이유)을 보존한 다음, [SKILL](SKILL.md)이 기술하는 방식대로 프로토타입을 보존하십시오. 선택된 것을 실제 코드에 반영하고 나머지는 main이 아니라 일회용 브랜치로 옮기십시오.

- **하위 형태 A**: 선택된 것을 기존 페이지에 반영하고, 선택되지 않은 변형과 전환기를 main에서 제거하십시오.
- **하위 형태 B**: 선택된 변형을 실제 라우트로 승격하고, 일회용 라우트와 전환기를 main에서 제거하십시오.

변형 전체가 1차 자료이므로, 쓰레기통이 아니라 일회용 브랜치에 들어갑니다. main 브랜치에 남겨진 변형 컴포넌트와 전환기는 빠르게 부패하고 다음 독자를 혼란스럽게 하기 때문입니다.

## 안티 패턴

- **색상이나 문구만 다른 변형.** 그것은 프로토타입이 아니라 조정입니다. 진짜 변형은 구조에 대해 의견이 다릅니다.
- **변형 간에 너무 많은 코드를 공유.** 공유 `<Header>`는 괜찮지만, 공유 `<Layout>`은 요점을 무너뜨립니다. 각 변형은 레이아웃을 자유롭게 버릴 수 있어야 합니다.
- **변형을 실제 변경 작업에 연결.** 읽기 전용 프로토타입은 괜찮습니다. 변형이 변경을 해야 한다면 스텁을 가리키게 하십시오. 질문은 "백엔드가 동작하는가"가 아니라 "이것은 어떻게 보여야 하는가"입니다.
- **프로토타입을 바로 프로덕션으로 승격.** 변형 코드는 프로토타입 제약(테스트 없음, 최소한의 오류 처리) 아래에서 작성되었습니다. 반영할 때 제대로 다시 작성하십시오.
