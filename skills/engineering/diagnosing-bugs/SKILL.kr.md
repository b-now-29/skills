# 버그 진단

어려운 버그를 위한 규율입니다. 명시적으로 정당화되는 경우에만 단계를 건너뛰십시오.

코드베이스를 탐색할 때, 관련 모듈에 대한 명확한 멘탈 모델을 얻기 위해 `GLOSSARY.md`(있는 경우)를 읽고, 작업 중인 영역의 ADR을 확인하십시오.

## 민감 정보 삭제

이 스킬에서는 명령, 출력, 캡처한 산출물을 보여 주게 됩니다. **먼저 모든 시크릿을 삭제하십시오**. 그 자리에 `<REDACTED>`를 쓰십시오. 루프는 환경 변수를 기반으로 구축하여, 자격 증명이 보여 주는 내용이 아니라 환경에 머무르도록 하십시오. 캡처한 산출물에는 인증 헤더가 포함되어 있습니다. 신호를 담고 있는 줄만 인용하십시오.

삭제된 출력만으로는 버그를 진단하기에 충분하지 않다면, 그렇게 말하고 사용자에게 물으십시오.

## 1단계: 피드백 루프 구축

**이것이 이 스킬의 핵심입니다.** 그 밖의 모든 것은 기계적입니다. 버그에 대한 **촘촘한(tight)** 통과/실패 신호(_이_ 버그에서 red가 되는 신호)가 있다면 원인을 찾게 될 것입니다. 이분 탐색, 가설 검증, 계측은 모두 그 신호를 소비할 뿐입니다. 그러한 신호가 없다면, 코드를 아무리 들여다보아도 구원받지 못합니다.

여기에 불균형할 정도로 많은 노력을 쏟으십시오. **공격적으로 하십시오. 창의적으로 하십시오. 포기하기를 거부하십시오.**

### 구축하는 방법, 대략 다음 순서로

1. 버그에 도달하는 어떤 시임에서든 **실패하는 테스트**: 단위, 통합, e2e.
2. 실행 중인 개발 서버를 대상으로 하는 **Curl / HTTP 스크립트**.
3. 픽스처 입력으로 **CLI 호출**하고, stdout을 알려진 정상 스냅샷과 비교.
4. UI를 조작하고 DOM/콘솔/네트워크에 대해 단언하는 **헤드리스 브라우저 스크립트**(Playwright / Puppeteer).
5. **캡처한 트레이스 재생.** 실제 네트워크 요청 / 페이로드 / 이벤트 로그를 디스크에 저장하고, 격리된 상태에서 해당 코드 경로를 통해 재생합니다.
6. **일회용 하네스.** 단일 함수 호출로 버그 코드 경로를 실행하는, 시스템의 최소 부분 집합(서비스 하나, 목으로 대체한 의존성)을 띄웁니다.
7. **속성 / 퍼즈 루프.** 버그가 "가끔 잘못된 출력"이라면, 1000개의 무작위 입력을 실행하고 실패 유형을 찾습니다.
8. **이분 탐색 하네스.** 버그가 두 개의 알려진 상태(커밋, 데이터셋, 버전) 사이에서 나타났다면, `git bisect run`으로 실행할 수 있도록 "상태 X로 부팅, 확인, 반복"을 자동화합니다.
9. **차등 루프.** 같은 입력을 이전 버전과 새 버전(또는 두 개의 구성)에 실행하고 출력을 비교합니다.
10. **HITL bash 스크립트.** 최후의 수단입니다. 사람이 클릭해야 한다면, 루프가 여전히 구조화되도록 `scripts/hitl-loop.template.sh`로 _그 사람을_ 진행시키십시오. 캡처된 출력은 당신에게 다시 전달됩니다.

올바른 피드백 루프를 구축하면, 버그는 90% 해결된 것입니다.

### 루프 조이기

루프를 하나의 제품으로 다루십시오. _어떤_ 루프를 갖게 되면, 그것을 **조이십시오**.

- 더 빠르게 만들 수 있는가? (설정 캐시, 관련 없는 초기화 건너뛰기, 테스트 범위 좁히기.)
- 신호를 더 날카롭게 만들 수 있는가? ("충돌하지 않음"이 아니라 특정 증상에 대해 단언하기.)
- 더 결정적으로 만들 수 있는가? (시간 고정, 난수 시드 지정, 파일 시스템 격리, 네트워크 고정.)

30초짜리 불안정한 루프는 루프가 없는 것보다 거의 낫지 않습니다. 2초짜리 결정적인 루프는 촘촘하며, 디버깅의 초능력입니다.

### 비결정적 버그

목표는 깔끔한 재현이 아니라 **더 높은 재현율**입니다. 트리거를 100번 반복하고, 병렬화하고, 부하를 가하고, 타이밍 윈도우를 좁히고, sleep을 주입하십시오. 50% 확률로 나타나는 버그는 디버깅할 수 있지만 1%는 그렇지 않으므로, 디버깅할 수 있을 때까지 재현율을 계속 높이십시오.

### 정말로 루프를 구축할 수 없을 때

멈추고 그렇다고 명시적으로 말하십시오. 시도한 것을 나열하십시오. 사용자에게 다음을 요청하십시오. (a) 버그가 재현되는 환경에 대한 접근, (b) 민감 정보가 삭제된 캡처 산출물(HAR 파일, 로그 덤프, 코어 덤프, 타임스탬프가 있는 화면 녹화), 또는 (c) 임시 프로덕션 계측을 추가할 권한. 루프 없이 가설 수립으로 진행하지 **마십시오**.

### 완료 기준: red가 되는 촘촘한 루프

루프가 **촘촘하고** **red가 될 수 있을** 때 1단계가 완료됩니다. 즉, **이미 최소 한 번 실행한**(호출과 그 출력을 민감 정보를 삭제하여 보여 주십시오) **하나의 명령**(스크립트 경로, 테스트 호출, curl)을 명시할 수 있어야 하며, 그 명령은 다음을 만족해야 합니다.

- [ ] **red가 될 수 있음**: 실제 버그 코드 경로를 구동하고 **사용자가 말한 정확한 증상**에 대해 단언하므로, 이 버그에서 red가 되고 수정되면 green이 될 수 있습니다. "오류 없이 실행됨"이 아닙니다. _이 특정 버그를 잡을 수_ 있어야 합니다.
- [ ] **결정적임**: 매 실행마다 같은 판정(불안정한 버그의 경우, 위에서처럼 고정된 높은 재현율).
- [ ] **빠름**: 분이 아니라 초 단위.
- [ ] **에이전트가 실행 가능함**: 무인으로 실행할 수 있습니다. 사람의 개입은 `scripts/hitl-loop.template.sh`를 통해서만 가능합니다.

이 명령이 존재하기 전에 이론을 세우기 위해 코드를 읽고 있는 자신을 발견한다면, **멈추십시오. 곧바로 가설로 뛰어드는 것이 바로 이 스킬이 막는 실패입니다.** red가 될 수 있는 명령이 없으면 2단계도 없습니다.

## 2단계: 재현 + 최소화

루프를 실행하십시오. 버그가 나타나면서 red가 되는 것을 지켜보십시오.

다음을 확인하십시오.

- [ ] 루프가 근처에서 우연히 발생하는 다른 실패가 아니라, **사용자**가 설명한 실패 유형을 만들어 냅니다. 잘못된 버그 = 잘못된 수정.
- [ ] 실패가 여러 번의 실행에 걸쳐 재현됩니다(또는 비결정적 버그의 경우, 디버깅할 수 있을 만큼 충분히 높은 비율로 재현됩니다).
- [ ] 이후 단계에서 수정이 실제로 그것을 해결하는지 검증할 수 있도록, 정확한 증상(오류 메시지, 잘못된 출력, 느린 타이밍)을 포착했습니다.

### 최소화

red가 되면, 재현을 **여전히 red가 되는 가장 작은 시나리오**로 줄이십시오. 입력, 호출자, 구성, 데이터, 단계를 **한 번에 하나씩** 잘라 내고, 자를 때마다 루프를 다시 실행하며, 실패에 하중을 지탱하는 것만 남기십시오.

왜 이렇게 해야 하는가: 최소 재현은 3단계에서 가설 공간을 줄여 주며(의심할 움직이는 부품이 더 적게 남음), 5단계에서 깔끔한 회귀 테스트가 됩니다.

**남은 모든 요소가 하중을 지탱할 때** 완료됩니다. 그중 어느 하나라도 제거하면 루프가 green이 됩니다.

재현**하고** 최소화할 때까지 진행하지 마십시오.

## 3단계: 가설 수립

어느 것이든 검증하기 전에 **순위가 매겨진 3~5개의 가설**을 생성하십시오. 단일 가설 생성은 첫 번째로 그럴듯한 아이디어에 고착됩니다.

각 가설은 **반증 가능**해야 합니다. 그것이 하는 예측을 명시하십시오.

> 형식: "<X>가 원인이라면, <Y를 변경>하면 버그가 사라질 것이다 / <Z를 변경>하면 버그가 악화될 것이다."

예측을 명시할 수 없다면, 그 가설은 느낌일 뿐입니다. 폐기하거나 날카롭게 다듬으십시오.

**검증하기 전에 순위가 매겨진 목록을 사용자에게 보여 주십시오.** 사용자는 종종 순위를 즉시 바꾸는 도메인 지식("방금 #3에 대한 변경을 배포했어요")을 가지고 있거나, 이미 배제한 가설을 알고 있습니다. 비용이 적은 체크포인트이며, 큰 시간 절약이 됩니다. 이 때문에 진행을 막지 마십시오. 사용자가 AFK라면 자신의 순위대로 진행하십시오.

## 4단계: 계측

각 프로브는 3단계의 특정 예측에 대응해야 합니다. **한 번에 하나의 변수만 바꾸십시오.**

도구 선호 순서:

1. 환경이 지원한다면 **디버거 / REPL 검사**. 중단점 하나가 로그 열 개보다 낫습니다.
2. 가설들을 구별하는 경계에서의 **표적화된 로그**.
3. "모든 것을 로그로 남기고 grep하기"는 절대 하지 마십시오.

**모든 디버그 로그에 태그를 다십시오.** 고유한 접두사를 사용하십시오(예: `[DEBUG-a4f2]`). 마지막 정리가 단 한 번의 grep이 됩니다. 태그가 없는 로그는 살아남고, 태그가 있는 로그는 사라집니다.

**성능 분기.** 성능 회귀의 경우, 로그는 대개 잘못된 도구입니다. 대신 기준 측정치(타이밍 하네스, `performance.now()`, 프로파일러, 쿼리 계획)를 확립한 다음, 이분 탐색하십시오. 먼저 측정하고, 그다음에 수정하십시오.

## 5단계: 수정 + 회귀 테스트

회귀 테스트는 **수정 전에** 작성하되, 이를 위한 **올바른 시임**이 있는 경우에만 작성하십시오.

올바른 시임이란 테스트가 호출 지점에서 발생하는 그대로의 **실제 버그 패턴**을 실행하는 곳입니다. 사용 가능한 유일한 시임이 너무 얕다면(버그에 여러 호출자가 필요한데 단일 호출자 테스트, 버그를 촉발한 연쇄를 재현할 수 없는 단위 테스트), 그곳의 회귀 테스트는 잘못된 확신을 줍니다.

**올바른 시임이 존재하지 않는다면, 그 자체가 발견 사항입니다.** 기록하십시오. 코드베이스 아키텍처가 버그를 고정하는 것을 막고 있는 것입니다. 다음 단계를 위해 이를 표시하십시오.

올바른 시임이 존재한다면:

1. 최소화된 재현을 그 시임에서 실패하는 테스트로 바꾸십시오.
2. 실패하는 것을 지켜보십시오. 코드나 픽스처를 변경하여 강제로 red를 만들었다면, 그것을 신뢰하기 전에 깨끗한 사본과 `diff`하여 변경이 반영되었음을 증명하십시오.
3. 수정을 적용하십시오.
4. 통과하는 것을 지켜보십시오.
5. 원래의(최소화하지 않은) 시나리오를 대상으로 1단계 피드백 루프를 다시 실행하십시오.

## 6단계: 정리

완료를 선언하기 전에 필수입니다.

- [ ] 원래의 재현이 더 이상 재현되지 않음(1단계 루프를 다시 실행)
- [ ] 회귀 테스트가 통과함(또는 시임이 없다는 것이 문서화됨)
- [ ] 모든 `[DEBUG-...]` 계측이 제거됨(접두사를 `grep`)
- [ ] 일회용 프로토타입이 삭제됨(또는 명확하게 표시된 디버그 위치로 이동됨)
- [ ] 다음 디버거가 배울 수 있도록, 정답으로 밝혀진 가설이 커밋 / PR 메시지에 명시됨
