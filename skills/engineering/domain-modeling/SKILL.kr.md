# 도메인 모델링

설계하면서 프로젝트의 도메인 모델을 능동적으로 구축하고 정제하십시오. 이것은 *능동적인* 규율입니다. 용어에 이의를 제기하고, 엣지 케이스 시나리오를 만들어 내며, 용어집과 결정이 결정화되는 순간 이를 기록합니다. (어휘를 위해 `GLOSSARY.md`를 단순히 *읽는* 것은 이 스킬이 아닙니다. 그것은 어떤 스킬이든 할 수 있는 한 줄짜리 습관입니다. 이 스킬은 모델을 단지 소비하는 것이 아니라 변경할 때를 위한 것입니다.)

## 파일 구조

대부분의 저장소는 단일 컨텍스트를 가집니다.

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

루트에 `GLOSSARY-MAP.md`가 존재한다면, 저장소는 여러 컨텍스트를 가집니다. 지도는 각 컨텍스트가 어디에 있는지 가리킵니다.

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← system-wide decisions
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← context-specific decisions
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

파일은 지연 생성하십시오. 즉, 작성할 무언가가 있을 때만 생성합니다. `GLOSSARY.md`가 없다면 첫 번째 용어가 확정될 때 생성하십시오. `docs/adr/`가 없다면 첫 번째 ADR이 필요할 때 생성하십시오.

## 세션 중

### 용어집을 기준으로 이의 제기

사용자가 `GLOSSARY.md`의 기존 언어와 충돌하는 용어를 사용하면, 즉시 지적하십시오. "용어집은 '취소(cancellation)'를 X로 정의하는데, 당신은 Y를 의미하는 것 같습니다. 어느 쪽입니까?"

### 모호한 언어 다듬기

사용자가 모호하거나 과적된 용어를 사용하면, 정확한 표준 용어를 제안하십시오. "'계정(account)'이라고 말씀하시는데, 고객(Customer)을 의미합니까, 사용자(User)를 의미합니까? 그 둘은 다른 것입니다."

### 구체적인 시나리오 논의

도메인 관계를 논의할 때, 구체적인 시나리오로 스트레스 테스트를 하십시오. 엣지 케이스를 탐색하고 사용자가 개념 간의 경계에 대해 정확해지도록 강제하는 시나리오를 만들어 내십시오.

### 코드와 교차 확인

사용자가 무언가가 어떻게 동작하는지 말하면, 코드가 그에 동의하는지 확인하십시오. 모순을 발견하면 드러내십시오. "코드는 주문(Order) 전체를 취소하는데, 방금 부분 취소가 가능하다고 말씀하셨습니다. 어느 쪽이 맞습니까?"

### GLOSSARY.md를 즉석에서 업데이트

용어가 확정되면, 그 자리에서 `GLOSSARY.md`를 업데이트하십시오. 일괄 처리하지 마십시오. 일어나는 대로 포착하십시오. [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)의 형식을 사용하십시오.

`GLOSSARY.md`에는 구현 세부 사항이 전혀 없어야 합니다. `GLOSSARY.md`를 명세, 메모장, 또는 구현 결정의 저장소로 취급하지 마십시오. 그것은 용어집이며, 그 외의 아무것도 아닙니다.

### ADR은 아껴서 제안

다음 세 가지가 모두 참일 때만 ADR 생성을 제안하십시오.

1. **되돌리기 어려움**: 나중에 마음을 바꾸는 비용이 의미 있을 정도로 큼
2. **맥락 없이는 놀라움**: 미래의 독자가 "왜 이렇게 했지?"라고 궁금해할 것임
3. **실제 트레이드오프의 결과**: 진정한 대안이 있었으며, 특정한 이유로 그중 하나를 선택함

세 가지 중 하나라도 빠지면 ADR을 건너뛰십시오. [ADR-FORMAT.md](./ADR-FORMAT.md)의 형식을 사용하십시오.
