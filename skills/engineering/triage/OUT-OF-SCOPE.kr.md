# 범위 외 지식 베이스

저장소의 `.out-of-scope/` 디렉터리는 거절된 기능 요청에 대한 영구적인 기록을 저장합니다. 두 가지 목적이 있습니다.

1. **조직의 기억**: 기능이 왜 거절되었는지 기록하여, 이슈가 종료될 때 그 근거가 사라지지 않도록 합니다
2. **중복 제거**: 이전의 거절과 일치하는 새 이슈가 들어오면, 스킬이 다시 논쟁하는 대신 이전 결정을 드러낼 수 있습니다

## 디렉터리 구조

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

이슈당이 아니라 **개념**당 하나의 파일입니다. 같은 것을 요청하는 여러 이슈는 하나의 파일 아래에 묶입니다.

## 파일 형식

파일은 데이터베이스 항목보다는 짧은 설계 문서처럼, 편안하고 읽기 쉬운 문체로 작성해야 합니다. 단락, 코드 샘플, 예시를 사용하여 처음 접하는 사람에게도 근거가 명확하고 유용하도록 하십시오.

```markdown
# 다크 모드

이 프로젝트는 다크 모드나 사용자용 테마를 지원하지 않습니다.

## 범위에서 제외되는 이유

렌더링 파이프라인은 `ThemeConfig`에 정의된 단일 색상 팔레트를 전제로 합니다.
여러 테마를 지원하려면 다음이 필요합니다.

- 컴포넌트 트리 전체를 감싸는 테마 컨텍스트 프로바이더
- 컴포넌트별 테마 인식 스타일 해석
- 사용자 테마 선호를 위한 영속성 계층

이는 콘텐츠 작성에 집중하는 프로젝트의 방향과 맞지 않는 상당한 아키텍처
변경입니다. 테마는 출력을 임베드하거나 재배포하는 하위 사용자의 관심사입니다.

```ts
// The current ThemeConfig interface is not designed for runtime switching:
interface ThemeConfig {
  colors: ColorPalette; // single palette, resolved at build time
  fonts: FontStack;
}
```

## 이전 요청

- #42: "Add dark mode support"
- #87: "Night theme for accessibility"
- #134: "Dark theme option"
```

### 파일 이름 짓기

개념에 대해 짧고 설명적인 kebab-case 이름을 사용하십시오: `dark-mode.md`, `plugin-system.md`, `graphql-api.md`. 디렉터리를 둘러보는 사람이 파일을 열지 않고도 무엇이 거절되었는지 이해할 수 있을 만큼 알아보기 쉬운 이름이어야 합니다.

### 근거 작성

근거는 실질적이어야 합니다. "우리는 이것을 원하지 않는다"가 아니라 그 이유를 써야 합니다. 좋은 근거는 다음을 참조합니다.

- 프로젝트의 범위나 철학("이 프로젝트는 X에 집중한다. 테마는 하위 사용자의 관심사다")
- 기술적 제약("이를 지원하려면 Y가 필요한데, 이는 우리의 Z 아키텍처와 충돌한다")
- 전략적 결정("…때문에 B 대신 A를 사용하기로 했다")

근거는 지속적이어야 합니다. 일시적인 상황("지금은 너무 바쁘다")을 언급하지 마십시오. 그것은 진짜 거절이 아니라 연기입니다.

## `.out-of-scope/`를 확인해야 하는 경우

트리아지 중(1단계: 컨텍스트 수집)에 `.out-of-scope/`의 모든 파일을 읽으십시오. 새 이슈를 평가할 때:

- 요청이 기존의 범위 외 개념과 일치하는지 확인하십시오
- 일치 여부는 키워드가 아니라 개념 유사성으로 판단합니다. "야간 테마"는 `dark-mode.md`와 일치합니다
- 일치하는 것이 있다면 유지 관리자에게 드러내십시오. "이것은 `.out-of-scope/dark-mode.md`와 유사합니다. 이전에 [근거] 때문에 거절했습니다. 여전히 같은 생각이십니까?"

유지 관리자는 다음 중 하나를 할 수 있습니다.

- **확인**: 새 이슈가 기존 파일의 "이전 요청" 목록에 추가된 다음, 종료됩니다
- **재고**: 범위 외 파일이 삭제되거나 업데이트되고, 이슈는 일반 트리아지를 거칩니다
- **이견**: 이슈들이 관련은 있지만 별개이므로, 일반 트리아지를 진행합니다

## `.out-of-scope/`에 기록해야 하는 경우

**개선 요청**(버그가 아님)이 `wontfix`로 *거절된* 경우에만 기록합니다. 이는 이슈와 정확히 같은 방식으로 개선 PR에도 적용됩니다. 같은 요청이 새로운 코드로 다시 돌아오지 않도록, 거절된 PR도 여기에 기록됩니다.

무언가가 **이미 구현되어 있어서** `wontfix`로 종료되는 경우에는 여기에 기록하지 **마십시오**. 그것은 거절된 기능이 아니라 구축된 기능입니다. 이를 기록하면 잘못된 거절로 중복 제거 검사를 오염시키게 됩니다. 대신 종료 댓글에서 해당 기능이 이미 있는 곳을 가리키십시오.

흐름:

1. 유지 관리자가 기능 요청이 범위 밖이라고 결정합니다
2. 일치하는 `.out-of-scope/` 파일이 이미 존재하는지 확인합니다
3. 있다면: 새 이슈를 "이전 요청" 목록에 덧붙입니다
4. 없다면: 개념 이름, 결정, 근거, 첫 번째 이전 요청을 담은 새 파일을 생성합니다
5. 결정을 설명하고 `.out-of-scope/` 파일을 언급하는 댓글을 이슈에 게시합니다
6. `wontfix` 라벨과 함께 이슈를 종료합니다

## 범위 외 파일 업데이트 또는 제거

유지 관리자가 이전에 거절한 개념에 대해 생각을 바꾸는 경우:

- `.out-of-scope/` 파일을 삭제하십시오
- 스킬이 오래된 이슈를 다시 열 필요는 없습니다. 그것들은 역사적 기록입니다
- 재고를 촉발한 새 이슈는 일반 트리아지를 거칩니다
