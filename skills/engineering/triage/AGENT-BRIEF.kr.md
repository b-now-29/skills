# 에이전트 브리프 작성

에이전트 브리프(agent brief)는 GitHub 이슈나 PR이 `ready-for-agent`로 이동할 때 게시되는 구조화된 댓글입니다. AFK 에이전트가 작업의 근거로 삼는 권위 있는 명세입니다. 원래의 본문과 토론은 맥락이며, 에이전트 브리프가 계약입니다.

브리프는 **에이전트가 무엇을 해야 하는지**를 기술하며, 이는 두 창구 모두에 적용됩니다. 이슈의 경우 아무것도 없는 상태에서 변경을 구축하는 것이고, PR의 경우 *기존 diff에 대해* 남은 일, 즉 마무리하고, 빈틈을 메우고, 리뷰 지적 사항을 처리하는 것입니다. 원칙은 어느 쪽이든 같으며, 아래의 PR 예시가 그 차이를 보여 줍니다.

## 원칙

### 정밀함보다 지속성

이슈는 며칠 또는 몇 주 동안 `ready-for-agent`에 머물러 있을 수 있습니다. 그동안 코드베이스는 바뀝니다. 파일의 이름이 바뀌거나, 이동하거나, 리팩터링되더라도 유용하게 남도록 브리프를 작성하십시오.

- 인터페이스, 타입, 동작 계약을 **기술하십시오**
- 에이전트가 찾거나 수정해야 할 구체적인 타입, 함수 시그니처, 구성 형태의 **이름을 명시하십시오**
- 파일 경로를 **참조하지 마십시오**. 낡게 됩니다
- 줄 번호를 **참조하지 마십시오**
- 현재의 구현 구조가 그대로 유지될 것이라고 **가정하지 마십시오**

### 절차가 아니라 동작

시스템을 **어떻게** 구현할지가 아니라 시스템이 **무엇을** 해야 하는지 기술하십시오. 에이전트는 코드베이스를 새로 탐색하고 스스로 구현 결정을 내릴 것입니다.

- **좋음:** "`SkillConfig` 타입은 `CronExpression` 타입의 선택적 `schedule` 필드를 받아야 한다"
- **나쁨:** "src/types/skill.ts를 열고 42번째 줄에 schedule 필드를 추가하라"
- **좋음:** "사용자가 인수 없이 `/triage`를 실행하면, 주의가 필요한 이슈의 요약을 보아야 한다"
- **나쁨:** "메인 핸들러 함수에 switch 문을 추가하라"

### 완전한 수락 기준

에이전트는 언제 끝났는지 알아야 합니다. 모든 에이전트 브리프에는 구체적이고 테스트 가능한 수락 기준이 있어야 합니다. 각 기준은 독립적으로 검증 가능해야 합니다.

- **좋음:** "`gh issue list --label needs-triage`를 실행하면 초기 분류를 거친 이슈가 반환된다"
- **나쁨:** "트리아지가 올바르게 동작해야 한다"

### 명시적인 범위 경계

무엇이 범위 밖인지 명시하십시오. 이는 에이전트가 과도하게 꾸미거나 인접 기능에 대해 가정하는 것을 막아 줍니다.

## 템플릿

```markdown
## 에이전트 브리프

**범주:** bug / enhancement
**요약:** 무엇이 이루어져야 하는지에 대한 한 줄 설명

**현재 동작:**
지금 무슨 일이 일어나는지 기술하십시오. 버그의 경우, 이것은 망가진 동작입니다.
개선의 경우, 이것은 기능이 기반으로 하는 현재 상태입니다.

**원하는 동작:**
에이전트의 작업이 완료된 후 무슨 일이 일어나야 하는지 기술하십시오.
엣지 케이스와 오류 조건에 대해 구체적으로 작성하십시오.

**핵심 인터페이스:**
- `TypeName`: 무엇이 바뀌어야 하며 그 이유
- `functionName()` 반환 타입: 현재 무엇을 반환하며 무엇을 반환해야 하는지
- 구성 형태: 필요한 새로운 구성 옵션

**수락 기준:**
- [ ] 구체적이고 테스트 가능한 기준 1
- [ ] 구체적이고 테스트 가능한 기준 2
- [ ] 구체적이고 테스트 가능한 기준 3

**범위 외:**
- 이 이슈에서 변경하거나 다루어서는 안 되는 것
- 관련 있어 보일 수 있지만 별개인 인접 기능
```

## 예시

### 좋은 에이전트 브리프 (버그)

```markdown
## 에이전트 브리프

**범주:** bug
**요약:** 스킬 description 잘라내기가 단어 중간에서 끊어져 깨진 출력을 만든다

**현재 동작:**
스킬 description이 1024자를 초과하면, 단어 경계와 관계없이 정확히
1024자에서 잘린다. 이로 인해 단어 중간에서 끝나는 description이
만들어진다(예: "Use when the user wants to confi").

**원하는 동작:**
잘라내기는 1024자 이전의 마지막 단어 경계에서 끊고, 잘렸음을 나타내기
위해 "..."를 덧붙여야 한다.

**핵심 인터페이스:**
- `SkillMetadata` 타입의 `description` 필드: 타입 변경은 필요 없지만,
  이를 채우는 검증/처리 로직이 단어 경계를 존중해야 한다
- SKILL.md 프런트매터를 읽고 description을 추출하는 모든 함수

**수락 기준:**
- [ ] 1024자 미만의 description은 변경되지 않는다
- [ ] 1024자를 초과하는 description은 1024자 이전의 마지막 단어 경계에서
      잘린다
- [ ] 잘린 description은 "..."로 끝난다
- [ ] "..."를 포함한 전체 길이가 1024자를 초과하지 않는다

**범위 외:**
- 1024자 제한 자체를 변경하는 것
- 여러 줄 description 지원
```

### 좋은 에이전트 브리프 (개선)

```markdown
## 에이전트 브리프

**범주:** enhancement
**요약:** 거절된 기능 요청을 추적하기 위한 `.out-of-scope/` 디렉터리 지원 추가

**현재 동작:**
기능 요청이 거절되면, 이슈는 `wontfix` 라벨과 댓글과 함께 종료된다.
결정이나 그 근거에 대한 영구적인 기록이 없다. 향후 유사한 요청이 오면
유지 관리자가 이전 논의를 기억하거나 검색해야 한다.

**원하는 동작:**
거절된 기능 요청은 결정, 근거, 그리고 해당 기능을 요청한 모든 이슈에 대한
링크를 담은 `.out-of-scope/<concept>.md` 파일에 문서화되어야 한다. 새 이슈를
트리아지할 때, 이 파일들과 일치하는지 확인해야 한다.

**핵심 인터페이스:**
- `.out-of-scope/`의 마크다운 파일 형식: 각 파일에는 `# Concept Name` 제목,
  `**Decision:**` 줄, `**Reason:**` 줄, 그리고 이슈 링크가 담긴
  `**Prior requests:**` 목록이 있어야 한다
- 트리아지 워크플로는 초기에 모든 `.out-of-scope/*.md` 파일을 읽고,
  들어오는 이슈를 개념 유사성으로 대조해야 한다

**수락 기준:**
- [ ] 기능을 wontfix로 종료하면 `.out-of-scope/`에 파일이 생성/업데이트된다
- [ ] 파일에는 결정, 근거, 종료된 이슈에 대한 링크가 포함된다
- [ ] 일치하는 `.out-of-scope/` 파일이 이미 존재하면, 중복을 만들지 않고
      새 이슈를 해당 파일의 "Prior requests" 목록에 덧붙인다
- [ ] 트리아지 중에 기존 `.out-of-scope/` 파일을 확인하고, 새 이슈가 이전
      거절과 일치하면 이를 드러낸다

**범위 외:**
- 자동 대조(사람이 일치 여부를 확인함)
- 이전에 거절된 기능을 다시 여는 것
- 버그 보고서(개선 요청의 거절만 `.out-of-scope/`에 기록됨)
```

### 좋은 에이전트 브리프 (PR)

PR의 경우, "현재 동작"은 diff의 상태를 기술하며, 브리프는 에이전트에게 처음부터 구축하는 것이 아니라 마무리하거나 수정하도록 요청합니다.

```markdown
## 에이전트 브리프

**범주:** enhancement
**요약:** 기여자의 `triage list`용 `--json` 출력 플래그를 마무리한다

**현재 동작:**
PR은 이슈 목록을 JSON으로 직렬화하는 `--json` 플래그를 추가한다. 정상 경로는
동작하며 diff는 프로젝트의 명령 구조와 일치한다. 두 가지 빈틈이 남아 있다.
오류가 여전히 (JSON이 아니라) 사람이 읽는 텍스트로 출력되며, 새 플래그에
테스트 커버리지가 없다.

**원하는 동작:**
`--json`을 사용하면, 모든 출력(오류 포함)이 stdout에 올바른 형식의 JSON으로
출력되며, 명령의 종료 코드는 변경되지 않는다. 플래그가 없을 때 기존의
사람이 읽는 출력은 그대로 유지된다.

**핵심 인터페이스:**
- 명령의 오류 경로는 `--json`에서 일반 텍스트 오류 대신
  `{ "error": string }`을 내보내야 한다
- PR이 이미 추가한 기존 직렬화기를 재사용한다. 두 번째 직렬화기를 도입하지 않는다

**수락 기준:**
- [ ] `triage list --json`이 성공과 오류 경우 모두에 대해 유효한 JSON을 내보낸다
- [ ] 종료 코드가 JSON이 아닌 명령과 일치한다
- [ ] 테스트가 `--json` 성공 출력과 하나의 오류 경우를 다룬다
- [ ] 기본(JSON이 아닌) 출력이 바이트 단위로 변경되지 않는다

**범위 외:**
- 다른 명령에 `--json`을 추가하는 것
- PR이 이미 정의한 성공 페이로드의 JSON 형태를 변경하는 것
```

### 나쁜 에이전트 브리프

```markdown
## 에이전트 브리프

**요약:** 트리아지 버그 수정

**할 일:**
트리아지 관련 기능이 망가졌다. 메인 파일을 보고 고쳐라.
150번째 줄 근처의 함수에 문제가 있다.

**변경할 파일:**
- src/triage/handler.ts (150번째 줄)
- src/types.ts (42번째 줄)
```

이것이 나쁜 이유:
- 범주가 없음
- 모호한 설명("트리아지 관련 기능이 망가졌다")
- 낡게 될 파일 경로와 줄 번호를 참조함
- 수락 기준이 없음
- 범위 경계가 없음
- 현재 동작 대 원하는 동작에 대한 설명이 없음
