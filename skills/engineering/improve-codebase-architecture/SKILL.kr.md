# 코드베이스 아키텍처 개선

아키텍처상의 마찰을 드러내고 **심화 기회(deepening opportunities)**, 즉 얕은 모듈을 깊은 모듈로 바꾸는 리팩터링을 제안하십시오. 목표는 테스트 가능성과 AI 탐색 용이성입니다.

이 명령은 프로젝트의 도메인 모델에 _기반하며_, 공유 설계 어휘 위에 구축됩니다.

- 아키텍처 어휘(**모듈(module)**, **인터페이스(interface)**, **깊이(depth)**, **시임(seam)**, **어댑터(adapter)**, **레버리지(leverage)**, **지역성(locality)**)와 그 원칙(삭제 테스트, "인터페이스가 곧 테스트 표면이다", "어댑터 하나 = 가상의 시임, 둘 = 실제 시임")을 위해 "codebase-design"으로 Skill 도구를 호출하십시오. 모든 제안에서 이 용어를 정확히 사용하고, "component", "service", "API", "boundary"로 표류하지 마십시오.
- `GLOSSARY.md`의 도메인 언어는 좋은 시임에 이름을 부여합니다. `docs/adr/`의 ADR은 이 명령이 다시 논쟁해서는 안 되는 결정을 기록합니다.

## 프로세스

### 1. 탐색

**탐색하기 전에 범위를 정하십시오: YAGNI.** 모듈을 심화하면 그 모듈에 대한 향후 변경이 쉬워지는 것으로 보답을 받으므로, 최근에 변경된 코드베이스 부분에 추가 가중치를 두십시오. 살펴보기 전에 *어디를* 살펴볼지 결정하십시오.

- 사용자가 방향(모듈, 하위 시스템, 고충 지점)을 지정했다면, 그것을 따르고 아래의 추론은 건너뛰십시오.
- 그렇지 않다면, 커밋 이력(`git log --oneline`)을 상당 부분 거슬러 올라가 코드베이스의 핫스폿, 즉 계속해서 등장하는 파일과 영역을 찾고, 그 경로들이 먼저 주의를 끌도록 하십시오. 변경이 뚜렷한 핫스폿 없이 흩어져 있다면, 범위를 넓히십시오.

먼저 프로젝트의 도메인 용어집(`GLOSSARY.md`)과 작업 중인 영역의 ADR을 읽으십시오.

그런 다음 새로운 컨텍스트 윈도우로 서브에이전트를 생성하여 코드베이스를 둘러보게 하십시오. 경직된 휴리스틱을 따르지 마십시오. 유기적으로 탐색하고 마찰을 경험하는 곳을 기록하십시오.

- 하나의 개념을 이해하기 위해 많은 작은 모듈 사이를 오가야 하는 곳은 어디인가?
- 인터페이스가 구현만큼 복잡한, **얕은** 모듈은 어디인가?
- 순수 함수가 테스트 가능성만을 위해 추출되었지만, 실제 버그는 그것이 호출되는 방식에 숨어 있는 곳(**지역성** 없음)은 어디인가?
- 강하게 결합된 모듈이 시임을 넘어 누수되는 곳은 어디인가?
- 코드베이스의 어느 부분이 테스트되지 않았거나, 현재 인터페이스를 통해 테스트하기 어려운가?

얕다고 의심되는 모든 것에 **삭제 테스트**를 적용하십시오. 그것을 삭제하면 복잡성이 집중되는가, 아니면 그저 이동하는가? "예, 집중된다"가 원하는 신호입니다.

### 2. 후보를 HTML 보고서로 제시

저장소에 아무것도 남지 않도록 OS 임시 디렉터리에 독립적인 HTML 파일을 작성하십시오. 임시 디렉터리는 `$TMPDIR`에서 확인하고, 없으면 `/tmp`(Windows에서는 `%TEMP%`)를 사용하며, 매 실행마다 새 파일이 생기도록 `<tmpdir>/architecture-review-<timestamp>.html`에 작성하십시오. 사용자를 위해 파일을 열고(Linux에서는 `xdg-open <path>`, macOS에서는 `open <path>`, Windows에서는 `start <path>`) 절대 경로를 알려 주십시오.

보고서는 레이아웃과 스타일링에 **CDN을 통한 Tailwind**를, 그래프/흐름/시퀀스가 구조를 안정적으로 전달하는 다이어그램에 **CDN을 통한 Mermaid**를 사용합니다. Mermaid를 직접 만든 CSS/SVG 시각 자료와 섞으십시오. 관계가 그래프 형태일 때(호출 그래프, 의존성, 시퀀스)는 Mermaid를, 더 편집적인 무언가(질량 다이어그램, 단면도, 축약 애니메이션)를 원할 때는 직접 만든 div/SVG를 사용하십시오. 각 후보는 **전/후 시각화**를 가집니다. 시각적으로 표현하십시오.

각 후보에 대해 다음을 담은 카드를 렌더링하십시오.

- **파일**: 어떤 파일/모듈이 관련되는지
- **문제**: 현재 아키텍처가 왜 마찰을 일으키는지
- **해결책**: 무엇이 바뀔지에 대한 평이한 언어의 설명
- **이점**: 지역성과 레버리지의 관점에서, 그리고 테스트가 어떻게 개선될지 설명
- **전 / 후 다이어그램**: 나란히 배치하고 직접 그린 것으로, 얕음과 심화를 보여 줌
- **권장 강도**: `Strong`, `Worth exploring`, `Speculative` 중 하나이며, 배지로 렌더링

보고서는 **최우선 권고(Top recommendation)** 섹션으로 끝내십시오. 어떤 후보를 가장 먼저 다룰 것이며 그 이유는 무엇인지입니다.

**도메인에는 GLOSSARY.md 어휘를, 아키텍처에는 `/codebase-design` 어휘를 사용하십시오.** `GLOSSARY.md`가 "Order"를 정의한다면, "FooBarHandler"나 "Order service"가 아니라 "Order 접수 모듈"에 대해 이야기하십시오.

**ADR 충돌**: 후보가 기존 ADR과 모순되는 경우, 마찰이 ADR을 재검토할 만큼 실제적일 때만 드러내십시오. 카드에 명확하게 표시하십시오(예: 경고 콜아웃: _"ADR-0007과 모순되지만, …때문에 다시 열어 볼 가치가 있음"_). ADR이 금지하는 모든 이론적인 리팩터링을 나열하지 마십시오.

전체 HTML 뼈대, 다이어그램 패턴, 스타일링 지침은 [HTML-REPORT.md](HTML-REPORT.md)를 참조하십시오.

아직 인터페이스를 제안하지 **마십시오**. 파일이 작성된 후, 사용자에게 물으십시오. "이 중 어떤 것을 탐색하고 싶으십니까?"

### 3. 그릴링 루프

사용자가 후보를 선택하면, "grilling"으로 Skill 도구를 호출하여 사용자와 함께 결정 트리를 진행하십시오. 제약 조건, 의존성, 심화된 모듈의 형태, 시임 뒤에 무엇이 있는지, 어떤 테스트가 살아남는지를 다룹니다.

결정이 결정화됨에 따라 부수 효과가 즉석에서 발생합니다. 진행하면서 도메인 모델을 최신 상태로 유지하기 위해 "domain-modeling"으로 Skill 도구를 호출하십시오.

- **`GLOSSARY.md`에 없는 개념의 이름을 심화된 모듈에 붙이고 있습니까?** 해당 용어를 `GLOSSARY.md`에 추가하십시오. 파일이 없다면 지연 생성하십시오.
- **대화 중에 모호한 용어를 다듬고 있습니까?** 그 자리에서 `GLOSSARY.md`를 업데이트하십시오.
- **사용자가 하중을 지탱하는 이유로 후보를 기각했습니까?** ADR을 제안하되, 다음과 같이 표현하십시오. _"향후 아키텍처 리뷰가 이를 다시 제안하지 않도록 ADR로 기록할까요?"_ 미래의 탐색자가 같은 것을 다시 제안하지 않기 위해 그 이유가 실제로 필요할 때만 제안하십시오. 일시적인 이유("지금은 할 가치가 없음")와 자명한 이유는 건너뛰십시오.
- **심화된 모듈에 대한 대안적인 인터페이스를 탐색하고 싶습니까?** "codebase-design"으로 Skill 도구를 호출하고, 그 두 번 설계하기(design-it-twice) 병렬 서브에이전트 패턴을 사용하십시오.
