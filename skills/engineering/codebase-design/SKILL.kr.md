# 코드베이스 설계

**깊은 모듈(deep module)**을 설계하십시오. 작은 인터페이스 뒤에 많은 동작을 두고, 깔끔한 시임에 배치하며, 그 인터페이스를 통해 테스트할 수 있도록 하는 것입니다. 코드를 설계하거나 재구성하는 곳이라면 어디서든 이 언어와 원칙을 사용하십시오. 목표는 호출자에게는 레버리지를, 유지 관리자에게는 지역성을, 모두에게는 테스트 가능성을 제공하는 것입니다.

## 용어집

이 용어를 정확히 사용하십시오. "component", "service", "API", "boundary"로 대체하지 마십시오. 일관된 언어가 핵심입니다.

**모듈(Module)**: 인터페이스와 구현을 가진 모든 것입니다. 의도적으로 규모에 무관합니다. 함수, 클래스, 패키지, 또는 계층을 가로지르는 슬라이스일 수 있습니다. _사용하지 말 것_: unit, component, service.

**인터페이스(Interface)**: 호출자가 모듈을 올바르게 사용하기 위해 알아야 하는 모든 것입니다. 타입 시그니처뿐만 아니라 불변 조건, 순서 제약, 오류 유형, 필수 구성, 성능 특성도 포함됩니다. _사용하지 말 것_: API, signature(너무 좁습니다. 이들은 타입 수준의 표면만을 가리킵니다).

**구현(Implementation)**: 모듈 내부에 있는 것, 즉 코드 본체입니다. **어댑터**와 구별됩니다. 무언가는 큰 구현을 가진 작은 어댑터(Postgres 저장소)일 수도, 작은 구현을 가진 큰 어댑터(메모리 내 가짜 객체)일 수도 있습니다. 시임이 주제일 때는 "어댑터"를, 그 밖의 경우에는 "구현"을 사용하십시오.

**깊이(Depth)**: 인터페이스에서의 레버리지입니다. 호출자(또는 테스트)가 배워야 하는 인터페이스 단위당 실행할 수 있는 동작의 양입니다. 많은 양의 동작이 작은 인터페이스 뒤에 있을 때 모듈은 **깊고(deep)**, 인터페이스가 구현만큼 복잡할 때 **얕습니다(shallow)**.

**시임(Seam)** _(Michael Feathers)_: 그 장소를 편집하지 않고도 동작을 바꿀 수 있는 곳입니다. 모듈의 인터페이스가 위치하는 *장소*입니다. 시임을 어디에 둘지는 그 뒤에 무엇이 들어가는지와는 별개의 고유한 설계 결정입니다. _사용하지 말 것_: boundary(DDD의 bounded context와 의미가 겹칩니다).

**어댑터(Adapter)**: 시임에서 인터페이스를 충족하는 구체적인 것입니다. 실체(내부에 무엇이 있는지)가 아니라 *역할*(어떤 자리를 채우는지)을 기술합니다.

**레버리지(Leverage)**: 호출자가 깊이로부터 얻는 것입니다. 배우는 인터페이스 단위당 더 많은 능력입니다. 하나의 구현이 N개의 호출 지점과 M개의 테스트에 걸쳐 보답합니다.

**지역성(Locality)**: 유지 관리자가 깊이로부터 얻는 것입니다. 변경, 버그, 지식, 검증이 호출자 전반에 퍼지지 않고 한곳에 집중됩니다. 한 번 고치면 모든 곳이 고쳐집니다.

## 깊은 모듈 대 얕은 모듈

**깊은 모듈** = 작은 인터페이스 + 많은 구현:

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**얕은 모듈** = 큰 인터페이스 + 적은 구현(피해야 함):

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

인터페이스를 설계할 때 다음을 물으십시오.

- 메서드의 수를 줄일 수 있는가?
- 매개변수를 단순화할 수 있는가?
- 더 많은 복잡성을 내부에 숨길 수 있는가?

## 원칙

- **깊이는 구현이 아니라 인터페이스의 속성입니다.** 깊은 모듈은 내부적으로 작고, 목으로 대체 가능하며, 교체 가능한 부분들로 구성될 수 있습니다. 그 부분들이 인터페이스의 일부가 아닐 뿐입니다. 모듈은 인터페이스의 **외부 시임**뿐만 아니라 **내부 시임**(구현에 비공개이며, 자체 테스트가 사용함)도 가질 수 있습니다.
- **삭제 테스트.** 모듈을 삭제한다고 상상해 보십시오. 복잡성이 사라진다면, 그것은 단순한 통과 지점이었습니다. 복잡성이 N개의 호출자 전반에 다시 나타난다면, 그 모듈은 제 몫을 하고 있었던 것입니다.
- **인터페이스가 곧 테스트 표면입니다.** 호출자와 테스트는 같은 시임을 가로지릅니다. 인터페이스를 *넘어서* 테스트하고 싶다면, 아마도 모듈의 형태가 잘못된 것입니다.
- **어댑터가 하나라면 가상의 시임입니다. 어댑터가 둘이라면 실제 시임입니다.** 시임을 가로질러 실제로 무언가가 달라지지 않는 한, 시임을 도입하지 마십시오.

## 테스트 가능성을 위한 설계

좋은 인터페이스는 테스트를 자연스럽게 만듭니다.

1. **의존성을 생성하지 말고 받아들이십시오.**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **부수 효과를 만들지 말고 결과를 반환하십시오.**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **작은 표면적.** 메서드가 적을수록 필요한 테스트가 적습니다. 매개변수가 적을수록 테스트 설정이 단순해집니다.

## 관계

- **모듈**은 정확히 하나의 **인터페이스**(호출자와 테스트에게 제시하는 표면)를 가집니다.
- **깊이**는 **모듈**의 속성이며, 그 **인터페이스**를 기준으로 측정됩니다.
- **시임**은 **모듈**의 **인터페이스**가 위치하는 곳입니다.
- **어댑터**는 **시임**에 위치하며 **인터페이스**를 충족합니다.
- **깊이**는 호출자에게 **레버리지**를, 유지 관리자에게 **지역성**을 만들어 냅니다.

## 기각된 관점

- **구현 줄 수 대 인터페이스 줄 수의 비율로서의 깊이**(Ousterhout): 구현을 부풀리는 것에 보상을 줍니다. 우리는 대신 레버리지로서의 깊이를 사용합니다.
- **TypeScript의 `interface` 키워드나 클래스의 public 메서드로서의 "인터페이스"**: 너무 좁습니다. 여기서 인터페이스는 호출자가 알아야 하는 모든 사실을 포함합니다.
- **"경계(Boundary)"**: DDD의 bounded context와 의미가 겹칩니다. **시임** 또는 **인터페이스**라고 말하십시오.

## 더 깊이 들어가기

- **의존성을 고려한 묶음의 심화**는 [DEEPENING.md](DEEPENING.md)를 참조하십시오. 의존성 범주, 시임 규율, 겹쳐 쌓지 말고 대체하는 테스트를 다룹니다.
- **대안적인 인터페이스 탐색**은 [DESIGN-IT-TWICE.md](DESIGN-IT-TWICE.md)를 참조하십시오. 병렬 서브에이전트를 띄워 근본적으로 다른 여러 방식으로 인터페이스를 설계한 다음, 깊이, 지역성, 시임 배치를 기준으로 비교합니다.
