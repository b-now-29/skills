# 심화

의존성을 고려하여 얕은 모듈의 묶음을 안전하게 심화하는 방법입니다. [SKILL.md](SKILL.md)의 어휘를 전제로 합니다: **모듈(module)**, **인터페이스(interface)**, **시임(seam)**, **어댑터(adapter)**.

## 의존성 범주

심화 후보를 평가할 때, 그 의존성을 분류하십시오. 범주에 따라 심화된 모듈이 시임을 가로질러 어떻게 테스트되는지가 결정됩니다.

### 1. 프로세스 내부 (In-process)

순수 계산, 메모리 내 상태, I/O 없음. 항상 심화할 수 있습니다. 모듈들을 병합하고 새로운 인터페이스를 통해 직접 테스트하십시오. 어댑터가 필요 없습니다.

### 2. 로컬 대체 가능 (Local-substitutable)

로컬 테스트 대역이 있는 의존성(Postgres에 대한 PGLite, 메모리 내 파일 시스템). 대역이 존재한다면 심화할 수 있습니다. 심화된 모듈은 테스트 스위트에서 실행되는 대역과 함께 테스트됩니다. 시임은 내부에 있으며, 모듈의 외부 인터페이스에 포트가 없습니다.

### 3. 원격이지만 소유함 (Ports & Adapters)

네트워크 경계 너머에 있는 자체 서비스(마이크로서비스, 내부 API). 시임에 **포트(port)**(인터페이스)를 정의하십시오. 깊은 모듈이 로직을 소유하고, 전송 계층은 **어댑터**로 주입됩니다. 테스트는 메모리 내 어댑터를 사용합니다. 프로덕션은 HTTP/gRPC/큐 어댑터를 사용합니다.

권장 형태: *"시임에 포트를 정의하고, 프로덕션용 HTTP 어댑터와 테스트용 메모리 내 어댑터를 구현하여, 네트워크에 걸쳐 배포되더라도 로직이 하나의 깊은 모듈에 위치하도록 하라."*

### 4. 진정한 외부 (Mock)

제어할 수 없는 서드파티 서비스(Stripe, Twilio 등). 심화된 모듈은 외부 의존성을 주입된 포트로 받으며, 테스트는 목(mock) 어댑터를 제공합니다.

## 시임 규율

- **어댑터가 하나라면 가상의 시임입니다. 어댑터가 둘이라면 실제 시임입니다.** 최소 두 개의 어댑터가 정당화되지 않는 한(일반적으로 프로덕션 + 테스트) 포트를 도입하지 마십시오. 어댑터가 하나뿐인 시임은 그저 간접 참조일 뿐입니다.
- **내부 시임 대 외부 시임.** 깊은 모듈은 인터페이스의 외부 시임뿐만 아니라 내부 시임(구현에 비공개이며, 자체 테스트가 사용함)도 가질 수 있습니다. 테스트가 사용한다는 이유만으로 내부 시임을 인터페이스를 통해 노출하지 마십시오.

## 테스트 전략: 겹쳐 쌓지 말고 대체하라

- 심화된 모듈의 인터페이스에서 테스트가 존재하게 되면, 얕은 모듈에 대한 기존 단위 테스트는 낭비가 됩니다. 삭제하십시오.
- 심화된 모듈의 인터페이스에서 새 테스트를 작성하십시오. **인터페이스가 곧 테스트 표면입니다**.
- 테스트는 내부 상태가 아니라 인터페이스를 통해 관찰 가능한 결과에 대해 단언합니다.
- 테스트는 구현이 아니라 동작을 기술하므로, 내부 리팩터링에도 살아남아야 합니다. 구현이 바뀔 때 테스트도 바뀌어야 한다면, 그 테스트는 인터페이스를 넘어서 테스트하고 있는 것입니다.
