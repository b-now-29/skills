# 두 번 설계하라

사용자가 선택한 심화 후보에 대해 대안적인 인터페이스를 탐색하고 싶어 할 때, 이 병렬 서브에이전트 패턴을 사용하십시오. "Design It Twice"(Ousterhout)에 기반합니다. 첫 번째 아이디어가 최선일 가능성은 낮습니다.

[SKILL.md](SKILL.md)의 어휘를 사용합니다: **모듈(module)**, **인터페이스(interface)**, **시임(seam)**, **어댑터(adapter)**, **레버리지(leverage)**.

## 프로세스

### 1. 문제 공간 구성

서브에이전트를 생성하기 전에, 선택된 후보의 문제 공간에 대해 사용자를 위한 설명을 작성하십시오.

- 새로운 인터페이스가 충족해야 할 제약 조건
- 인터페이스가 의존할 의존성과, 그 의존성이 속하는 범주([DEEPENING.md](DEEPENING.md) 참조)
- 제약 조건을 구체화하기 위한 대략적인 예시 코드 스케치. 제안이 아니라, 제약 조건을 구체적으로 만들기 위한 방법일 뿐입니다

이를 사용자에게 보여 준 다음, 즉시 2단계로 진행하십시오. 서브에이전트가 병렬로 작업하는 동안 사용자는 읽고 생각합니다.

### 2. 서브에이전트 생성

각각 새로운 컨텍스트 윈도우를 가진 3개 이상의 서브에이전트를 병렬로 생성하십시오. 각 서브에이전트는 심화된 모듈에 대해 **근본적으로 다른** 인터페이스를 만들어 내야 합니다.

각 서브에이전트에게 별도의 기술 지시서(파일 경로, 결합 세부 사항, [DEEPENING.md](DEEPENING.md)의 의존성 범주, 시임 뒤에 무엇이 있는지)를 프롬프트로 제공하십시오. 이 지시서는 1단계의 사용자용 문제 공간 설명과는 별개입니다. 각 에이전트에게 서로 다른 설계 제약을 부여하십시오.

- 에이전트 1: "인터페이스를 최소화하라. 최대 1~3개의 진입점을 목표로 하라. 진입점당 레버리지를 최대화하라."
- 에이전트 2: "유연성을 최대화하라. 많은 사용 사례와 확장을 지원하라."
- 에이전트 3: "가장 흔한 호출자에 최적화하라. 기본 사례를 사소하게 만들어라."
- 에이전트 4(해당하는 경우): "시임을 가로지르는 의존성에 대해 포트 & 어댑터를 중심으로 설계하라."

각 서브에이전트가 아키텍처 언어 및 프로젝트의 도메인 언어와 일관되게 이름을 짓도록, [SKILL.md](SKILL.md) 어휘와 GLOSSARY.md 어휘를 모두 지시서에 포함하십시오.

각 서브에이전트는 다음을 출력합니다.

1. 인터페이스(타입, 메서드, 매개변수, 그리고 불변 조건, 순서, 오류 유형)
2. 호출자가 이를 어떻게 사용하는지 보여 주는 사용 예시
3. 구현이 시임 뒤에 숨기는 것
4. 의존성 전략과 어댑터([DEEPENING.md](DEEPENING.md) 참조)
5. 트레이드오프: 레버리지가 높은 곳과 얇은 곳

### 3. 제시 및 비교

사용자가 각 설계를 흡수할 수 있도록 설계를 순차적으로 제시한 다음, 산문으로 비교하십시오. **깊이(depth)**(인터페이스에서의 레버리지), **지역성(locality)**(변경이 집중되는 곳), **시임 배치**를 기준으로 대조하십시오.

비교한 후에는 자신의 권고를 제시하십시오. 어떤 설계가 가장 강력하다고 생각하며 그 이유는 무엇인지입니다. 서로 다른 설계의 요소가 잘 결합될 수 있다면, 혼합안을 제안하십시오. 분명한 입장을 취하십시오. 사용자는 메뉴가 아니라 확실한 판단을 원합니다.
