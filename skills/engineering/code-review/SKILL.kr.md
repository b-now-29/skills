---

`HEAD`와 사용자가 제공하는 고정된 시점 사이의 diff에 대한 두 축의 리뷰입니다.

- **Standards**: 코드가 이 저장소의 문서화된 코딩 표준을 준수합니까?
- **Spec**: 코드가 원래의 이슈 / 명세를 충실하게 구현합니까?

두 축은 서로의 컨텍스트를 오염시키지 않도록 **병렬 서브에이전트**로 실행되며, 그런 다음 이 스킬이 그 발견 사항을 취합합니다. 모든 서브에이전트는 새로운 컨텍스트 윈도우로 시작하십시오.

이슈 트래커는 이미 제공되었어야 합니다. 그렇지 않다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 안내하십시오.

## 프로세스

### 1. 고정된 시점 확정

사용자가 말한 것이 무엇이든 그것이 고정된 시점입니다(커밋 SHA, 브랜치 이름, 태그, `main`, `HEAD~5` 등). 지정하지 않았다면 물어보십시오.

diff 명령을 한 번 확정하십시오: `git diff <fixed-point>...HEAD`(세 개의 점을 사용하므로 merge-base를 기준으로 비교합니다). `git log <fixed-point>..HEAD --oneline`으로 커밋 목록도 기록하십시오.

더 진행하기 전에, 고정된 시점이 해석되는지(`git rev-parse <fixed-point>`), 그리고 diff가 비어 있지 않은지 확인하십시오. 잘못된 참조나 빈 diff는 두 개의 병렬 서브에이전트 내부가 아니라 여기서 실패해야 합니다.

### 2. 명세 출처 식별

다음 순서로 원래의 명세를 찾으십시오.

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67` 등). 트래커 문서의 워크플로를 통해 가져옵니다.
2. 사용자가 인수로 전달한 경로.
3. 브랜치 이름이나 기능과 일치하는 `docs/`, `specs/`, `.scratch/` 아래의 명세 파일.
4. 아무것도 찾지 못했다면, 사용자에게 명세가 어디 있는지 물으십시오. 명세가 없다고 하면, **Spec** 서브에이전트는 건너뛰고 "사용 가능한 명세 없음"을 보고합니다.

### 3. 표준 출처 식별

코드를 어떻게 작성해야 하는지 문서화한 모든 파일을 저장소에서 찾으십시오. `CODING_STANDARDS.md` 또는 `CONTRIBUTING.md`가 존재한다면 반드시 목록에 있어야 합니다.

저장소가 문서화한 것이 무엇이든 그에 더하여, Standards 축은 항상 아래의 **코드 스멜 기준선(smell baseline)**을 가집니다. 이는 저장소가 아무것도 문서화하지 않았더라도 적용되는 Fowler 코드 스멜(_Refactoring_, 3장)의 고정된 집합입니다. 두 가지 규칙이 이를 구속합니다.

- **저장소가 우선합니다.** 문서화된 저장소 표준이 항상 이깁니다. 기준선이 지적할 무언가를 저장소 표준이 승인한다면, 해당 스멜을 억제하십시오.
- **항상 판단의 문제입니다.** 각 스멜은 라벨이 붙은 휴리스틱("Feature Envy 가능성")이며, 결코 엄격한 위반이 아닙니다. 여기의 다른 모든 표준과 마찬가지로, 도구가 이미 강제하는 것은 건너뛰십시오.

각 스멜은 *무엇인가* → *어떻게 고치는가* 순으로 읽습니다. diff와 대조하십시오.

- **Mysterious Name(불가사의한 이름)**: 무엇을 하는지 또는 무엇을 담는지 드러내지 않는 이름을 가진 함수, 변수, 타입. → 이름을 바꾸십시오. 정직한 이름이 떠오르지 않는다면 설계가 불분명한 것입니다.
- **Duplicated Code(중복 코드)**: 같은 로직 형태가 변경 내의 여러 hunk나 파일에 나타남. → 공유되는 형태를 추출하고, 양쪽에서 호출하십시오.
- **Feature Envy(기능 편애)**: 자신의 데이터보다 다른 객체의 데이터에 더 많이 손을 뻗는 메서드. → 메서드를 그것이 부러워하는 데이터 쪽으로 옮기십시오.
- **Data Clumps(데이터 뭉치)**: 같은 몇 개의 필드나 매개변수가 계속 함께 이동함(태어나고 싶어 하는 타입). → 하나의 타입으로 묶어 그것을 전달하십시오.
- **Primitive Obsession(기본형 집착)**: 고유한 타입을 가질 자격이 있는 도메인 개념을 기본형이나 문자열이 대신함. → 그 개념에 작은 고유 타입을 부여하십시오.
- **Repeated Switches(반복되는 스위치)**: 같은 타입에 대한 같은 `switch`/`if` 연쇄가 변경 전반에 걸쳐 반복됨. → 다형성, 또는 양쪽이 공유하는 하나의 맵으로 대체하십시오.
- **Shotgun Surgery(산탄총 수술)**: 하나의 논리적 변경이 diff 내 여러 파일에 걸친 산발적인 편집을 강제함. → 함께 바뀌는 것을 하나의 모듈로 모으십시오.
- **Divergent Change(뒤엉킨 변경)**: 하나의 파일이나 모듈이 서로 관련 없는 여러 이유로 편집됨. → 각 모듈이 한 가지 이유로만 바뀌도록 분할하십시오.
- **Speculative Generality(추측성 일반화)**: 명세에 없는 필요를 위해 추가된 추상화, 매개변수, 훅. → 삭제하십시오. 실제 필요가 드러날 때까지 인라인으로 되돌리십시오.
- **Message Chains(메시지 체인)**: 호출자가 의존해서는 안 되는 긴 `a.b().c().d()` 탐색. → 첫 번째 객체의 메서드 하나 뒤로 그 탐색을 숨기십시오.
- **Middle Man(중개자)**: 대부분 그저 위임만 하는 클래스나 함수. → 잘라 내고, 실제 대상을 직접 호출하십시오.
- **Refused Bequest(상속 거부)**: 상속받은 것의 대부분을 무시하거나 재정의하는 하위 클래스나 구현체. → 상속을 버리고 합성을 사용하십시오.

### 4. 두 서브에이전트를 병렬로 생성

두 서브에이전트 호출을 포그라운드에서 함께 실행하고, 그들이 반환하는 보고서를 취합하십시오.

**Standards 서브에이전트 프롬프트**에는 다음이 포함되어야 합니다.

- 전체 diff 명령과 커밋 목록.
- 3단계에서 찾은 표준 출처 파일 목록, **그리고 3단계의 스멜 기준선**을 전부 붙여 넣은 것(서브에이전트는 그 밖에 이에 접근할 방법이 없습니다).
- 지시 사항: "관련이 있는 경우 파일/hunk별로 다음을 보고하라. (a) diff가 문서화된 표준을 위반하는 모든 곳: 해당 표준(파일 + 규칙)을 인용하라. (b) 발견한 모든 기준선 스멜: 이름을 대고 해당 hunk를 인용하라. 엄격한 위반과 판단의 문제를 구별하라. 문서화된 표준의 위반은 엄격한 위반일 수 있지만, 기준선 스멜은 항상 판단의 문제이며, 문서화된 저장소 표준이 기준선보다 우선한다. 도구가 강제하는 것은 건너뛰라. 400단어 이내."

**Spec 서브에이전트 프롬프트**에는 다음이 포함되어야 합니다.

- diff 명령과 커밋 목록.
- 명세의 경로 또는 가져온 내용.
- 지시 사항: "다음을 보고하라. (a) 명세가 요청했지만 누락되었거나 부분적으로만 구현된 요구 사항, (b) diff에 있지만 요청되지 않은 동작(범위 확장), (c) 구현된 것처럼 보이지만 구현이 잘못되어 보이는 요구 사항. 각 발견 사항에 대해 명세의 해당 줄을 인용하라. 400단어 이내."

명세가 없다면, Spec 서브에이전트를 건너뛰고 최종 보고서에 이를 기록하십시오.

### 5. 취합

두 보고서를 `## Standards`와 `## Spec` 제목 아래에, 그대로 또는 가볍게 정리하여 제시하십시오. 발견 사항을 병합하거나 순위를 다시 매기지 **마십시오**. 두 축은 의도적으로 분리되어 있기 때문입니다(_두 축인 이유_ 참조).

한 줄 요약으로 끝맺으십시오. 축별 발견 사항 총수와, _각 축 내에서_ 가장 심각한 문제(있는 경우)입니다. 축을 넘나들며 하나의 승자를 고르지 마십시오. 그것이 바로 분리가 막기 위해 존재하는 순위 재조정입니다.

## 두 축인 이유

변경은 한 축을 통과하고 다른 축에서 실패할 수 있습니다.

- 모든 표준을 따르지만 잘못된 것을 구현한 코드 → **Standards 통과, Spec 실패.**
- 이슈가 요청한 것을 정확히 하지만 프로젝트의 관례를 깨는 코드 → **Spec 통과, Standards 실패.**

이를 따로 보고하면 한 축이 다른 축을 가리는 것을 막을 수 있습니다.
