# 티켓 트래커

> 2026-10에 조사되었으며, 최신 상태임을 보장하지 않습니다. 방향을 잡는 데 사용한 다음, 현재의 선택지를 직접 조사하십시오. 제품, 가격, 제한, 베타 상태는 빠르게 변합니다.

티켓 트래커는 팩토리의 사람용 인터페이스입니다. 아래의 각 유형은 출발점입니다. 그것이 무엇이며 팩토리가 언제 그것을 선택하는지 읽은 다음, [추가 조사](#추가-조사)의 질문에 비추어 예시를 확인하십시오.

## 유형

### 1. Git 호스트 트래커

git 호스트에 내장된 트래커로, 티켓, 브랜치, PR이 하나의 제품, 하나의 권한 모델, 하나의 ID를 공유합니다. 팩토리가 작거나, 팀이 이미 git 호스트에서 생활하거나, 저장소가 공개된 경우에 선택합니다. 이것이 "모두 GitHub에서" 설계입니다. git 호스트의 CI가 별도의 연결 코드 없이 오케스트레이터 자리를 채웁니다. 상태는 별도의 보드에 있으므로, 라벨이 믿을 수 있는 라우터입니다. 외부 개발자는 코드가 있는 곳에 제출하며, 개발자가 아닌 사람은 계정이 필요하므로 피드백 버튼이 API를 통해 제출합니다. 자체 호스팅 git 호스트는 트래커를 함께 가지고 다닙니다.

- [GitHub Issues](https://docs.github.com/en/copilot/concepts/agents/about-third-party-agents): 기본값. Copilot, Claude, Codex에 대한 에이전트 할당 기능.
- [GitLab Issues](https://about.gitlab.com/blog/how-to-use-a-work-item-created-trigger/): 작업 항목에서 트리거되는 Duo Agent Platform 흐름.
- [Forgejo](https://forgejo.org/2026-10-release-v17-0/): 자체 호스팅, Actions 호환.

검증할 것: 어떤 에이전트 할당 기능이 아직 프리뷰이며 어떤 요금제에 포함되는지, 네이티브 에이전트가 이후 댓글을 읽는지 아니면 할당 시점의 티켓만 읽는지(2026-10 기준, Copilot은 할당 시점에만 읽음).

### 2. 에이전트 네이티브 개발 트래커

에이전트를 일급 담당자로 취급하며, 에이전트 API와 자체 코딩 에이전트를 갖춘 소프트웨어 팀용 독립형 SaaS 트래커입니다. 제품, 지원, 디자인 담당자가 작업을 예약하는 경우, 팀이 이미 그곳에서 생활하는 경우, 또는 세련된 트리아지 및 계획 뷰를 원하는 경우에 선택합니다. "Linear 티켓" 설계입니다. 상태와 워크플로가 일급 개념이므로, "Ready로 이동됨"이 깔끔한 트리거가 됩니다. 에이전트는 사람이 위임하는 앱 사용자로 나타나며, 실행은 티켓에 진행 상황을 스트리밍할 수 있습니다. 이 유형의 네이티브 에이전트는 모든 유형 중 가장 깊이 통합되어 있으므로, 오케스트레이터와 러너 자리도 일부 채울 수 있습니다.

- [Linear](https://linear.app/developers/agents): 가장 에이전트 친화적인 트래커.
- [Jira](https://support.atlassian.com/jira-software-cloud/docs/collaborate-on-work-items-with-ai-agents/): 상태로 트리거되는 에이전트. 이미 Atlassian을 사용하는 조직에 적합합니다.
- [Shortcut](https://www.shortcut.com/help/integrations/using-ai-agents): 스토리를 할당하거나 댓글에서 에이전트를 멘션합니다.
- [YouTrack](https://www.jetbrains.com/youtrack/): 코드로 정의하는 워크플로. 자체 호스팅 가능.

검증할 것: 에이전트 API 상태(2026-10 기준, Linear는 개발자 프리뷰였음), 네이티브 에이전트 실행이 어떻게 측정되고 가격이 매겨지는지, 에이전트 좌석 비용, 에이전트 웹훅의 확인 응답 기한, 어떤 요금제가 고객용 양식을 여는지, 자체 호스팅 에디션의 지원 종료 날짜.

### 3. 오픈 소스 개발 트래커

자체 인프라에서 실행할 수 있는 Linear 스타일의 트래커로, 클라우드 에디션도 함께 있습니다. 데이터를 내부에 보관해야 하는 경우(에어갭, 규제 환경), 또는 사용자가 트래커를 구매하면서도 그 소스를 읽고 패치하고 싶은 경우에 선택합니다. 상태, 라벨, 사용자 정의 속성에 의한 라우팅은 유형 2와 거의 같게 동작하며, 네이티브 에이전트는 더 초기 단계입니다.

- [Plane](https://developers.plane.so/dev-tools/agents/overview): Linear와 유사. 앱별 봇 사용자. 에이전트가 댓글로 응답합니다.
- [Huly](https://github.com/hcengineering/huly-selfhost): 양방향 GitHub 동기화를 갖춘 올인원 작업 공간. 운영하기에는 무거운 스택입니다.
- [OpenProject](https://www.openproject.org/): 성숙한 고전적 프로젝트 관리 도구.

검증할 것: 에이전트 기능 상태(2026-10 기준, Plane은 베타였음), 어떤 에디션이 게스트 역할과 접수 양식을 제공하는지, 라이선스, 자체 호스팅 스택의 운영 비용.

### 4. 범용 업무 도구

데이터베이스나 작업 목록이 트래커를 겸하는 업무 관리 또는 문서 도구입니다. 이미 그곳에서 생활하는 비엔지니어링 팀을 위한 경우, 또는 티켓이 코드보다는 주로 콘텐츠, 운영, 조사인 경우에 선택합니다. 양식이 강점입니다. 링크를 가진 누구나 티켓을 제출할 수 있습니다. 라우팅은 유연한 데이터베이스 속성이므로, 모든 팩토리가 자체 스키마를 만들어 냅니다. 개발 맥락(diff, PR)은 git 호스트에서 한 번 더 클릭해야 볼 수 있습니다. SaaS 전용입니다.

- [Notion](https://www.notion.com/help/custom-agents): 트래커로서의 데이터베이스. 데이터베이스 변경 시 에이전트가 실행됩니다.
- [Asana](https://asana.com/product/ai/ai-teammates): AI Teammates가 할당된 작업을 맡습니다.
- [ClickUp](https://clickup.com/brain/cloud-agents): Cloud Agents가 작업 스레드에 PR을 돌려줍니다.
- [Trello](https://developer.atlassian.com/cloud/trello/guides/rest-api/webhooks/): 보드와 목록. 웹훅과 Butler 자동화.

검증할 것: 웹훅 지연 시간과 세분성(2026-10 기준, Notion은 콘텐츠 업데이트를 일괄 처리하여 1~2분 늦게 도착함), 어떤 요금제에 에이전트가 포함되는지.

### 5. 저장소 네이티브 트래커

저장소에 파일(JSONL, 마크다운)로 저장되는 티켓으로, 에이전트가 CLI나 MCP 서버를 통해 편집하고 코드처럼 병합됩니다. 한 명의 개발자가 로컬에서 에이전트를 운용하며 계획을 git에 두고 싶은 경우, 또는 실제 트래커 옆에서 실행의 작업 기억으로 사용하는 경우에 선택합니다. git 호스트로의 푸시가 유일한 트리거이므로, 오케스트레이터가 파일을 비교하여 무엇이 바뀌었는지 찾습니다. ID는 git 호스트의 것을 사용합니다. 외부 제출은 커밋이나 PR로, 모든 유형 중 가장 약하므로, 다른 사람들이 티켓을 제출하게 되면 팩토리는 git 호스트 트래커로 옮겨 갑니다.

- [Beads](https://github.com/steveyegge/beads): 의존성 추적을 갖춘 JSONL로, 실행이 차단되지 않은 다음 티켓을 선택할 수 있습니다.
- [Backlog.md](https://github.com/MrLesk/Backlog.md): 칸반 뷰와 MCP 서버를 갖춘 마크다운 작업.

### 6. 직접 구축

팩토리 자체의 앱이 자체 데이터베이스에 티켓을 보관하며, 대개 오케스트레이터 옆에 있습니다. "자체 트래커" 설계입니다. 트래커 자체가 *곧* 제품인 경우(내부 플랫폼, 고객 대상 지원 팩토리), 또는 어떤 기성 모델도 맞지 않는 경우에 선택합니다. 트리거는 함수 호출이 되며, 아래 질문의 모든 특성이 작성하고 유지 관리해야 할 코드가 됩니다. 이 스킬이 구매를 선호하는 이유가 바로 이것입니다. 웹훅을 갖춘 [Airtable](https://airtable.com/developers/web/api/webhooks-overview) 베이스는 반쯤 만들어진 중간 지점입니다.

## 추가 조사

각 후보를 다음 질문에 비추어 확인하십시오. 이 질문들이 자리를 결정합니다.

- **트리거**: 어떤 티켓 변경(생성, 라벨 지정, 상태 이동, 할당, 댓글, 멘션)이 오케스트레이터가 실행으로 바꿀 수 있는 웹훅이나 이벤트를 발생시킵니까? 얼마나 빠르고 얼마나 세분화되어 있습니까?
- **라우팅**: 실행이 자신의 종류(탐색, 구현, 재작업)를 알기 위해 읽을 수 있는 라벨, 상태, 필드는 무엇입니까?
- **스레드**: 사람이 댓글로 에이전트에게 답할 수 있으며, 그 답글이 다음 실행을 트리거합니까?
- **ID**: API와 봇 ID가 있어서, 실행이 자기 자신으로서 동작하고 사람이 에이전트와 동료를 구별할 수 있습니까? 봇에 좌석 비용이 듭니까?
- **네이티브 에이전트**: 티켓을 에이전트에게 직접 할당할 수 있습니까? 어떤 에이전트를, 어떤 요금제에서, 어떻게 측정합니까? 할당 시점의 티켓을 읽습니까, 아니면 전체 스레드를 읽습니까?
- **외부 제출**: 티켓 소스나 고객이 어떻게 티켓을 생성합니까? 양식, 이메일, 채팅, API? 어떤 요금제가 이를 엽니까?
- **호스팅**: SaaS 전용입니까, 아니면 자체 호스팅이 가능하며, 어떤 라이선스입니까?

답은 1차 자료에 있습니다. API 및 웹훅 참조(이벤트 목록, 페이로드, 전송 및 재시도 규칙), 에이전트 또는 앱 개발자 문서, 가격 페이지와 요금제 비교표, 변경 로그 또는 릴리스 노트입니다. 블로그 게시물이나 비교 사이트보다 이들을 우선하십시오.

가장 빨리 낡는 순서대로: 에이전트 기능과 그 프리뷰 또는 베타 상태, 에이전트 측정 방식과 크레딧 가격, 에이전트와 양식에 대한 요금제 제한, 속도 제한, 그리고 인수, 서비스 종료, 자체 호스팅 에디션의 지원 종료 날짜. 웹훅 이벤트 목록과 라우팅 모델은 천천히 변합니다.

## 오래 지속되는 함정

이에 의존하기 전에 각각이 여전히 유효한지 검증하십시오.

- **GitHub의 `GITHUB_TOKEN` 함정**: 기본 `GITHUB_TOKEN`으로 만든 변경은 새로운 워크플로 실행을 트리거하지 않습니다. 다음 실행을 트리거하기 위해 티켓에 라벨을 붙이거나 댓글을 다는 실행은 GitHub App 토큰을 통해 동작합니다.
- **할당 시점의 맥락**: 일부 네이티브 에이전트는 할당될 때만 티켓을 읽으므로, 이후의 맥락은 PR에 둡니다.
- **에이전트 웹훅은 빠른 확인 응답을 기대합니다**: 오케스트레이터는 즉시 확인 응답을 보내고 그 후에 실행을 시작합니다.
- **범용 업무 도구의 일괄 처리된 웹훅**은 늦게 도착합니다. 신속한 실행이 필요한 팩토리는 속성 변경을 트리거로 사용하거나 다른 유형을 선택합니다.
