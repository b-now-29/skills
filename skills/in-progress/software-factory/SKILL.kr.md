**소프트웨어 팩토리(software factory)**는 티켓, PR, 일정을 병합된 코드로 바꾸어 사용자가 선택한 원격 인프라에 배포하는 에이전트 시스템입니다. 이 스킬은 소프트웨어 팩토리를 설계하기 위한 언어입니다. 팩토리를 논의하거나 화이트보드에 그릴 때는 이 용어들을, 그리고 오직 이 용어들만 사용하십시오. 사용자가 _사용하지 말 것_ 아래에 있는 단어를 쓰면, 표준 용어를 알려 주십시오.

## 작업과 실행

**작업(Task)**:
팩토리가 수행하는 일의 종류로, 한 번 정의되어 여러 번 실행됩니다. 리뷰, 탐색, 구현, 래칫(ratchet) 등입니다. 작업은 티켓, PR, 또는 코드베이스 전체를 대상으로 할 수 있습니다.
_사용하지 말 것_: job, workflow, action

**트리거(Trigger)**:
실행을 시작하는 이벤트입니다. 티켓 트래커나 git 호스트의 변경, 오케스트레이터의 시계, 또는 다른 실행입니다.

**실행(Run)**:
하나의 러너에서 하나의 작업을 트리거부터 종료까지 한 번 실행하는 것으로, 블랙박스로 취급됩니다. 실행은 직접, 오케스트레이터의 로직을 통해, 또는 티켓 트래커나 git 호스트를 변경함으로써 추가 실행을 트리거합니다. 실행은 결코 사람을 기다리지 않습니다. 실행은 종료되고, 이후 사람이 티켓 트래커나 git 호스트에 가한 변경이 새로운 실행을 트리거합니다.
_사용하지 말 것_: session

**러너(Runner)**:
실행이 수행되는 일회용 머신입니다. 머신 자체가 오래 유지되더라도, 그 위의 어떤 것도 실행이 끝난 후 남지 않습니다. 실행이 이전 실행에 대해 가지는 유일한 기억은 티켓 트래커, git 호스트, 오케스트레이터입니다.
_사용하지 말 것_: server, host, box, compute, sandbox

## 서비스

**티켓 트래커(Ticket tracker)**:
티켓이 있는 곳이자 팩토리의 사람용 인터페이스입니다. 사람은 티켓을 제출하여 작업을 예약하고, 댓글로 에이전트와 대화하며, 사람이 티켓에 가한 변경이 실행을 트리거합니다.
_사용하지 말 것_: issue tracker, ticket manager, project board

**티켓 소스(Ticket source)**:
티켓 트래커에 티켓을 생성하는, 팩토리 외부의 모든 것입니다. 피드백 버튼, 모니터, 오류 추적기, 받은 편지함 등입니다.
_사용하지 말 것_: data source, trigger source, intake

**Git 호스트(Git host)**:
브랜치, PR, 리뷰가 있는 곳입니다.
_사용하지 말 것_: code host, forge, repo

**오케스트레이터(Orchestrator)**:
트리거를 받아 러너에서 실행을 시작하고, 어떤 실행이 대기 중이거나, 진행 중이거나, 완료되었는지 기록하는 구성 요소입니다.
_사용하지 말 것_: dispatcher, scheduler, control plane

**관측 플랫폼(Observability platform)**:
러너가 로그, 트레이스, 상태를 보내는 곳으로, 사람이 각 실행 내부에서 무슨 일이 일어났는지 볼 수 있게 합니다. 선택 사항입니다. 러너나 오케스트레이터 자리를 채우는 제품이 그 자체로 충분한 정보를 보여 주는 경우가 많습니다. 무언가가 이를 티켓 트래커나 git 호스트에 기록하기 전까지, 실행은 결코 이를 근거로 판단하지 않습니다.
_사용하지 말 것_: observability, logs, monitoring, dashboard

## 팩토리 설계하기

설계에는 두 개의 절반이 있습니다. 각각 하나의 제품으로 채워지는 자리인 **서비스**와, 그 실행이 서비스를 통해 작업을 진행시키는 **작업**입니다.

팩토리가 아니라 사용자의 문제에서 시작하십시오. 트리아지되지 않은 티켓, 자동 리뷰를 기다리는 PR, 마이그레이션해야 할 더 엄격한 자동 검사, 아무도 읽지 않는 버그 등입니다. 사용자가 문제를 언급하거나 무엇을 만들어야 할지 모를 때는, 흔한 문제를 해결하는 작업에 대해 [EXAMPLE-TASKS.md](EXAMPLE-TASKS.md)를 읽으십시오.

### 천천히 시작하십시오

모든 트리거는 가속 페달입니다. 브레이크 없는 가속 페달은 쓰레기 대포(slop cannon)를 만듭니다. 세 가지 브레이크가 있습니다.

- **자동화된 검사**: 모든 실행이 통과해야 하는 결정적인 관문(타입, 린트, 테스트).
- **자동화된 리뷰**: 코드베이스의 표준과, 티켓이 있는 경우 그 티켓을 기준으로 diff를 선입견 없이 읽는 별도의 실행.
- **사람의 리뷰**: PR이 병합되기 전에 사람이 읽습니다. 사람이 잡아낸 것은 새로운 자동화된 검사와 더 날카로운 자동화된 리뷰가 됩니다.

한 번에 하나의 자동 트리거를 추가하고, 처음에는 조절하며(버그 보고서 열 개 중 하나, 하루에 한 번 울리는 시계), 모든 PR에 사람의 리뷰를 두십시오. 브레이크가 신뢰를 얻음에 따라 조절을 풀고, 모든 실행 루프는 사람에게 넘어가기 전에 몇 번의 시도로 상한을 두십시오.

### 모든 자리를 채우십시오

각 서비스는 하나의 자리입니다. 하나의 제품이 여러 자리를 채울 수 있으며, 하나의 서버가 여러 서비스를 호스팅할 수 있습니다. 세 가지 설계를 나란히 비교하면 다음과 같습니다.

| 서비스           | 모두 GitHub에서                      | Linear 티켓                         | 자체 트래커              |
| ---------------- | ------------------------------------ | ----------------------------------- | ------------------------- |
| 티켓 트래커      | GitHub Issues                        | Linear                              | 자체 앱                   |
| 티켓 소스        | 피드백 버튼                          | 피드백 버튼, 모니터                 | 피드백 버튼, 모니터       |
| Git 호스트       | GitHub                               | GitHub                              | GitHub                    |
| 오케스트레이터   | GitHub Actions                       | 자체 서버 + 데이터베이스            | 자체 앱                   |
| 러너             | Actions 러너                         | Actions, E2B, Daytona 또는 VPS      | 자체 앱, 또는 샌드박스    |
| 관측 플랫폼      | 없음: Actions 실행 페이지로 충분     | LLM 트레이싱 플랫폼                 | 자체 앱                   |

사용자가 어떤 자리에 들어갈 제품을 고르고 있다면, 그 자리의 조사 문서를 읽어 방향을 잡은 다음, 현재의 선택지를 직접 조사하십시오. 각 조사 문서는 선택지를 유형별로 묶고 그 자리를 결정하는 질문을 나열합니다.

- [TICKET-TRACKERS.md](TICKET-TRACKERS.md)
- [GIT-HOSTS.md](GIT-HOSTS.md)
- [RUNNERS.md](RUNNERS.md)
- [OBSERVABILITY-PLATFORMS.md](OBSERVABILITY-PLATFORMS.md)

서비스는 구매하고 작업은 직접 만드십시오. 작업은 사용자의 설계를 담고, 서비스는 범용적입니다. 기성 티켓 트래커를 선호하십시오. 견고하고, 사람들이 이미 알고 있으며, 외부 사용자를 들이기 쉽습니다.

### 모든 작업에 질문하십시오

각 작업에 대해 답하십시오.

1. 무엇이 이를 트리거합니까?
2. 무엇을 하며, 어떤 서비스를 읽고 씁니까?
3. 다음에 무엇을 트리거합니까?
4. 사람은 어디에서 다시 개입합니까?
5. 두 실행이 같은 작업을 하는 것을 무엇이 막습니까?

각 티켓 소스에 대해 답하십시오. 같은 티켓을 두 번 제출하는 것을 무엇이 막습니까?

모든 자리에 제품(관측 플랫폼의 경우 의도적인 없음)이 명시되고, 모든 작업과 티켓 소스가 모든 질문에 대한 답을 가지면 설계가 완료된 것입니다.
